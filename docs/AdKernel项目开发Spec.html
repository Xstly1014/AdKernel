AdKernel · 实时广告决策引擎（RTA）项目开发 Spec v2

v2 相对 v1 的本质升级：从"一个高 QPS 决策接口"升级为"一条会呼吸的投放链路"。补齐转化归因回流、特征近线更新、对账、可观测告警、降级总开关、频控与多计划隔离——按未来需要上线的标准设计的完整业务闭环。简历时间线：2026年04月 – 07月（接替 GuardLM 位置）。

01业务初心与定位

业务初心（面试讲故事的完整动机链）

这是 v2 最重要的一节。项目为什么存在，必须用业务回答，不能用 JD 回答。

叙事环节内容
场景主体一家电商平台在抖音系媒体投放拉新广告，日预算十万级，年投放花费千万级
痛点传统投放靠人群包圈人：人群包 T+1 更新——用户昨天刚下单，今天的拉新广告照投给他（重复投放 = 纯浪费）；沉睡的高价值用户没有差异化出价（机会成本）；低质流量无法在曝光前拒绝（预算流失）
方案RTA：媒体每次广告曝光前实时调用广告主接口，广告主用一方数据（订单、会员状态、行为频次）在毫秒级窗口决策"参竞与否 + 出价系数"——决策从离线搬到在线，从静态搬到实时
有效性证明不是"做完了"，是"证明有效"：AB 对照实验（RTA 策略组 vs 人群包基线组），报表对比 CPA / 参竞质量 / 预算利用率——技术优化直接产生用户增长价值
事故视角上线不是终点：超花一分钱都是事故（防超花 + 对账）；RTA 超时率过高会被媒体降权甚至关停（超时预算硬约束的业务来源）；投放事故的第一响应是降级总开关（一键全量退出参竞）
一句话初心：让广告主的每一分预算在每一次曝光机会上都被实时审视——该拒的拒、该加价的加价、已转化的立刻排除。整个系统的每个模块都能追溯到这句话：特征服务（拿一方数据）、策略引擎（定拒放规则）、预算控制（守住钱袋）、归因回流（闭环验证）、AB 实验（证明价值）。

定位：与 mini-MQ 的拼图关系

维度mini-MQAdKernel
项目形态中间件（造轮子）业务服务（用轮子造车）
流量形态写密集（持久化/刷盘/副本）读密集（缓存/无状态/低延迟）
一致性难点副本间一致性（HW/epoch）缓存一致性 + 预算一致性 + 归因正确性
闭环AdKernel 的埋点与转化回流走 mini-MQ——"造了轮子，还造了用轮子的车"；对账结论直接引用 mini-MQ 的零丢失实证

闭环判定标准
每个箭头都有数据流动、有异常出口、有对账兜底。面试讲出来是"我设计了一条会呼吸的投放链路"：投放配置影响决策 → 决策产生消耗 → 消耗回流归因 → 归因更新特征 → 特征反过来改变下一次决策 → AB 实验持续验证策略价值。任何一环断掉，系统就退化回静态人群包。

一次请求的延迟预算分解（60ms 口径）

环节预算超支动作
网络往返（本地仿真）~5ms—
接入层校验 + 幂等 + 反序列化~10ms超时返回默认策略
特征查询（L1 命中为快路径）~15ms超时走 stale 兜底缓存（巨量实证口径 12min）
策略求值 + 预算预扣~15ms策略异常不阻断，走默认策略 + 告警埋点
响应序列化~5ms—
合计目标P99 < 50ms全程软超时：宁可保守决策，绝不超时（超时率过高会被媒体降权）

03里程碑路线（M0–M5，约 9-10 周）

延续深入手册模式：每里程碑单独产出深入手册（问题驱动→决策矩阵→执行→验收→坑速查表）。v2 里程碑相对 v1 的变化：M2 加多计划与频控，M3 加对账与降级总开关，M4 重构为归因回流 + AB 实验的完整闭环里程碑。

M0 · 业务域建模与媒体模拟器（1 周）

要解决的问题：没有严格对手方，就没有真实约束。媒体模拟器必须扮演三种角色：流量生产者、业务合法性校验者、转化回传与账单生成者。

任务验收预期
1. 广告域模型成文（docs/domain.md，约 15 个名词）：用户/广告计划/广告位/出价系数/预算/频控/曝光/点击/转化/归因/人群包/实验分桶/pacing/对账/超时率后续所有里程碑无歧义引用；每个名词带"为什么需要它"
2. RTA 协议定义（HTTP/JSON，对齐业界字段：requestId/userId/campaignId/adSlotId/scene → target/bidRatio）+ 转化回传协议（曝光/点击/转化事件）+ 模拟账单格式三份协议文档齐全，请求/回传/账单各有样例
3. 媒体模拟器：QPS 曲线（含洪峰时段）、用户分布（热头部 + 长尾）、决策合法性断言能打 1 万+ QPS；断言生效：黑名单用户参竞 → 模拟器报错
4. echo 骨架（恒参竞）+ 转化回传模拟（按 CTR→CVR 概率漏斗）全链路闭环跑通；延迟基线数字落盘（后续优化对照）

M1 · 特征服务与多级缓存（1.5 周）

要解决的问题：决策依赖用户特征，特征查不快一切白谈；特征查不对（穿透/过期），决策就是错的。

任务验收预期
1. 模拟画像库：Redis 预置 50 万用户特征（会员等级/黑名单/最近转化时间/行为频次）数据生成脚本可复现
2. L1 Caffeine + L2 Redis 两级缓存L1 命中率 ≥ 80%（热用户分布），命中/未命中延迟对比数字
3. 防穿透：空值缓存 + 布隆过滤器（非法用户 ID）混入 10% 伪造 ID，画像库零穿透放行
4. 超时降级：特征超时走 stale 兜底 → 默认画像（保守策略）注入 Redis 延迟，决策不超时、降级率可观测

M2 · 策略引擎、多计划路由与频控（1.5 周）

要解决的问题：多计划并存时的隔离与路由；策略是业务的大脑——改策略不停服、策略坏了不拖垮主链路、新策略先灰度再全量。

任务验收预期
1. 多计划路由：请求按 campaignId 路由到独立预算/策略/人群，互不串扰双计划并行压测，消耗/决策各归各账
2. 规则 DSL（表达式引擎）：承载真实语义策略——"已购未满 7d → 不参竞；沉默高价值 → bidRatio 1.5；黑名单 → 拒"5+ 条广告人话策略可配置运行
3. 频控：用户×计划维度的曝光次数上限（滑动窗口）超频用户第二次请求被策略层拒绝，频控命中率可观测
4. 热更新 + 灰度：AtomicReference 原子切换；新策略先经 AB 分流放 5% 流量压测中改策略 QPS 零抖动；灰度比例可调、可一键回退
5. 安全降级：策略异常不阻断主链路（默认策略 + 告警埋点）注入策略抛异常，决策成功率不降

M3 · 限流、预算、对账与降级总开关（2 周）

要解决的问题：限流是八股，预算是业务——超花一分钱都是事故；预算防线没有对账兜底不完整；故障时要有保命开关。

任务验收预期
1. QPS 限流：令牌桶（先 Guava 后可自写）；过载返回限流码，媒体侧不重试风暴洪峰注入（模拟器洪峰曲线），过载流量平滑拒绝
2. 预算三级防线：请求前预扣（滑动窗口）→ 埋点后异步校正 → 超支熔断消耗跑满预算，最终超支率 < 1.5%（对齐简历 bullet 与 M3 手册验收口径）
3. pacing 匀速消耗：按时间片分配额度（巨量"防超投防挤兑"同款问题）消耗曲线平缓 vs 不做 pacing 的前松后紧对照曲线
4. 跨天边界：预算按自然日重置，跨零点请求归属正确（时钟边界测试）零点前后压测，无重复预算/无预算泄漏
5. 对账：T+1 比对模拟媒体账单 vs 自记消耗，差异定位流程成文（归属窗口/去重口径）账单差异 = 0；人为注入差异（重复回传/乱序）能定位到根因
6. 降级总开关：一键全量退出参竞（投放事故第一响应）压测中触发，决策立即 100% 拒绝，QPS 不掉

M4 · 归因回流、特征近线更新与 AB 实验（2 周）

要解决的问题：v2 的灵魂里程碑——没有回流，"已购即排除"就是静态名单，系统自己打自己脸。AB 平台的价值不是技术组件，是证明 RTA 有效。

任务验收预期
1. 归因引擎：曝光→点击→转化事件按末次点击归因到计划/实验组（简化口径，成文说明）归因正确性校验脚本：抽样 1000 条转化，归属 100% 正确
2. 特征近线回流：转化事件 → mini-MQ → 特征更新消费者 → L2 失效 → "已转化即排除"转化发生到下次请求被排除，端到端延迟 < 5s；对账零丢失（引用 mini-MQ 结论）
3. AB 分流平台：一致性哈希分桶（同用户同桶）+ 分层正交分流稳定性 100%，分组流量比 <1% 偏差
4. RTA vs 人群包对照实验：基线组用静态人群包决策，实验组用完整 RTA 链路，报表对比 CPA/参竞质量/预算利用率报表能讲出业务结论：RTA 组 CPA 更优，差异可归因（排除了多少已购、加价了多少高价值用户）
mini-MQ 依赖隔离：特征回流管道经接口抽象，mini-MQ 未就绪时降级为直接批量消费落库（M4 不阻塞）。切换故事本身是面试素材。

M5 · 压测、可观测与收官（1.5 周）

要解决的问题：P99 < 50ms 是军令状；没有可观测的系统不敢上线；收官交付物要支撑简历与面试。

任务验收预期
1. 全景压测：QPS 阶梯 + 延迟曲线 + 拐点（单机容量结论）吞吐-P99 曲线；复用 mini-MQ M5 纪律（预热/3 轮/P99）
2. 火焰图归因 + GC 调优（JFR + jfr2flame）≥2 组四段式调优战报（现象→归因占比→改动→复测）
3. 可观测面板 + 告警规则：决策率/P99/降级率/预算消耗速率；消耗速率异常 → 疑似超花 P0 告警面板能回放一次注入事故（预算熔断/特征降级）的完整曲线
4. 收官档案：README（10 分钟跑通）+ ADR 0001-0009 + 战报 + 简历 bullet 定稿数字组汇总表全部两跳可溯源；深挖题脱稿

04关键技术决策（ADR 预告，M5 收口成文）

#决策否决的备选判据
0001媒体模拟器三合一：流量生成 + 业务合法性断言 + 转化回传/账单现成压测工具（JMeter/wrk）压测工具只会发流量，不会校验业务正确性，也不会产生回流数据——闭环转不起来
0002L1 Caffeine + L2 Redis 两级缓存，L1 优先只 Redis / 只本地巨量实证：L1 常驻、特征超时走 stale 兜底；纯 Redis 每跳 ~1ms 网络放大
0003策略引擎：表达式引擎 + 策略模式框架 + 原子热更新硬编码 if-else / 重量级规则引擎（Drools）ADX 实证模式；改策略不发版；策略异常不阻断主链路
0004预算预扣 + 异步校正 + 超支熔断三级防线 + pacing单点实时扣减 / 事后对账防超花是限流的业务化；pacing 是巨量防超投同款问题
0005归因口径：末次点击归因首次点击 / 多点加权归因简化口径但显式成文（ADR 声明边界）；多点归因需要 Shapley 类模型，超出工程项目边界——知道边界比堆功能成熟
0006幂等：requestId 内存 LRU 去重窗口不做幂等 / Redis 全局去重媒体重试是常态；LRU 窗口覆盖重试时间尺度，Redis 去重把快路径变慢路径
0007对账 T+1 文件比对 + 差异定位流程不做对账（信任自记消耗）计费对不上是广告系统 P0 事故；对账是预算防线的最后兜底
0008策略发布灰度复用 AB 分流（先 5% 后全量）独立灰度系统 / 直接全量AB 分流天然是灰度基础设施——一次建设两处受益；直接全量 = 拿全量预算赌新策略
0009埋点与特征回流走 mini-MQ同步落库 / 直接批量写库主链路零阻塞铁律 + 两个项目互相成就 + 可靠性结论复用

降级线

  • 核心线（不可砍）：M0 + M1 + M3 + M5 —— 协议与对手方、多级缓存、限流预算对账、压测数字 + 可观测面板。简历最低保障：低延迟 API + 缓存 + 预算 + 压测调优
  • 增强线：M4 归因回流与 AB 对照实验 —— v2 的灵魂，时间再紧也建议保住"归因 + 特征回流"（闭环叙事），可砍对照实验报表（保留分流）
  • 裁剪顺序：先砍 M4 对照实验报表 → 再砍 M2 灰度与频控（保留 DSL 与多计划）→ M0/M1/M3/M5 永不砍

AdKernel 实时广告决策引擎（RTA） | 后台开发 | 2026年04月 -- 2026年07月
背景: 广告主侧 RTA 系统——媒体每次广告曝光前实时询问"是否参竞、出价系数
多少"，广告主基于订单、会员、行为等一方数据在毫秒级窗口内完成决策，替代
传统 T+1 人群包，解决已购用户重复投放、高价值用户无法差异化出价的投放效率问题。

▸ 实时决策链路: 媒体对决策接口的超时率设有清退红线，超时即丧失参竞资格。
  设计五级决策流水线，逐级设定超时预算与降级出口，保障流量突增与局部故障
  下决策服务持续可用；全链路 P99 38ms @ 3.2万 QPS
▸ 广告预算防超花: 广告投放"决策在前、扣费在后"，天然存在无法撤回的超花
  窗口，超花即投放事故。设计预算预扣、异步校正、超支熔断三级防线，配合
  匀速消耗策略控制投放节奏，日预算超支率 <1.5%；T+1 对账媒体账单与内部
  消耗，差异定位流程化清零
▸ 转化回流数据闭环: 传统人群包 T+1 更新导致已转化用户次日仍被重复触达，
  预算持续浪费。构建"转化回传→归因→特征回流"近线更新链路，"已转化即排除"
  端到端延迟 <5s，用户特征时效由 T+1 提升至秒级
▸ AB 实验体系: 为量化 RTA 相对人群包的业务价值，构建用户维度分流与实验
  指标体系，完成 RTA 与人群包基线的随机对照实验，验证转化成本（CPA）优化
  12%，为投放模式选择提供数据依据
数字校准对照（与 resume0.2.tex 注释互链）：P99 38ms/3.2万 QPS = M5 全景压测；超支<1.5%、对账清零 = M3 预算防线与对账四桶；<5s 回流 = M4 归因链路实测；CPA 12% = M4 对照实验报表。四条 bullet 的数字全部两跳可溯源，M5 收官时逐项对账。

08面试深挖题（15 题，M5 手册逐题完整作答）

#题答题锚点
1这个项目解决什么业务问题？业务初心链（01 节）：人群包 T+1 → 重复投放浪费 → RTA 毫秒级决策；收尾"让每一分预算在每次曝光上被实时审视"
2RTA 和 RTB 的区别？筛选 vs 竞价：入场资格审核 vs 拍卖场；RTA 性能要求更苛刻——还没拿到入场资格已在消耗时间预算
360ms 延迟预算怎么分配？五段分解；理念：超时预算显式化 + 每级有降级出口；超时率过高被媒体降权是业务来源
4怎么证明 RTA 有效？AB 对照实验设计：基线=静态人群包、实验=完整链路；看 CPA/参竞质量；差异可归因（排除了多少已购、加价了多少高价值）
5"已转化即排除"怎么实现的？链路延迟多少？转化回传 → mini-MQ → 特征消费更新 → L2 失效 → 下次请求排除；<5s；为什么够快：事件驱动而非轮询
6防超花怎么设计？三级防线 + pacing + 对账兜底；"超花一分钱都是事故"——限流的业务化
7对账对不上怎么排查？差异定位流程：归属窗口（跨天边界）/ 重复回传（幂等）/ 乱序（时间戳）；对账是预算防线最后兜底
8策略热更新怎么保证线程安全？灰度怎么做？AtomicReference 原子切换；灰度复用 AB 分流先 5%——一次建设两处受益
9特征查询超时怎么办？stale 兜底（巨量 12min 实证）→ 默认画像保守策略；降级率可观测、可告警
10媒体重复请求怎么办？requestId LRU 去重窗口：覆盖重试时间尺度；去重放快路径（内存），不做 Redis 全局去重（慢路径）
11频控为什么在策略层做而不是接入层？频控是业务规则（每计划不同上限），接入层只做通用防护——分层原则
12跨零点预算怎么算？自然日重置 + 归属窗口显式化（23:59:59 的消耗归昨天）；时钟边界测试
13为什么埋点异步化？主链路零阻塞铁律；内存聚合摊薄；mini-MQ 对账零丢失结论直接复用
14读高并发和写高并发（mini-MQ）差别？缓存命中率 vs 刷盘吞吐；无状态水平扩 vs 副本一致性；软超时降级 vs 故障转移
15和真实广告系统差多远？诚实边界：裁剪了召回/排序/出价模型（算法团队领域）；归因简化为末次点击（显式 ADR）；我聚焦工程约束（延迟/预算/降级/闭环），工程侧与生产同构
