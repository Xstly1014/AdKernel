AdKernel · M1 深入手册

特征是决策的原料，缓存是低延迟的命。M1 给 M0 的 echo 骨架装上真实特征引擎：画像源（模拟广告主一方数据）→ L1 Caffeine（纳秒级）→ L2 Redis（毫秒级）→ 源（5ms 注入延迟）三级读路径，加防穿透双层与超时降级链。M1 结束时：特征查询 P99 从 ~12ms 降至 ~2ms，L1 命中率 ≥80%，Redis 注入延迟下决策不超时。性能叙事数字「L1 命中率 85%、12ms→2ms」在本册变成实测——按 Spec v2 定版原则它们不上简历，是决策链路 bullet 的面试追问弹药。

00M1 的定位与伏笔

为什么特征服务是 M1 而不是决策逻辑问题驱动

M0 的 echo 恒参竞，延迟基线是"裸奔"数字。真实决策链中特征查询是延迟预算最大的可变项（15ms 预算）：L1 命中则微秒级返回，未命中穿透到源则 5ms 起步，Redis 抖动则必须降级。先把这 15ms 的确定性做出来，M2 的策略求值才有稳定的舞台——地基不稳，上面的策略再聪明也会被延迟抖动拖垮。另一个动机：特征模型的字段设计直接由 M2 策略需求反推（每个字段都能说出哪条策略消费它），所以 M1 顺带锁定了特征契约。

本册埋的伏笔

M1 埋的线在哪收
特征含 lastConvertTime 字段M2 策略"已购未满 7d 不参竞"的数据源；M4 转化回流更新的目标字段
一致性预算：L1 15s / L2 5min / stale 12min（巨量实证）M3 降级链路的分层语义；面试答"缓存不一致窗口怎么定"的依据
三级命中率 + 降级率指标（recordStats）M5 可观测面板直接接入
L1 容量=10 万条（热头部 20%）的推导过程M5 压测拐点分析的素材：容量调大/调小的命中率曲线
特征查询延迟分解数字性能叙事「12ms→2ms」的两跳溯源终点（面试追问弹药）

01任务1 · 画像源与特征模型

要解决的问题问题驱动

真实 RTA 查的是广告主一方数据（订单库/会员库/行为日志），不可能被 RTA 服务直连——中间必须有特征服务。我们的仿真要回答三个问题：源是什么、特征长什么样、源层"慢"在哪里（没有慢的源，缓存的一切优化都无法度量）。

决策一：画像源的形态

方案内容判定
真 DB（H2/MySQL）50 万用户建表导入× 引入无关复杂度（连接池/JDBC 调优是另一个项目的事），且"慢"不可控
内存 Map + 延迟注入（采用）50 万画像进 ConcurrentHashMap，查询时注入 5ms 处理延迟（模拟 DB 网络往返 + 查询）✓ 零依赖、延迟可控可调（压测时可注入 50ms 模拟抖动）、50 万对象 ~100MB 内存可承受
L2 Redis 直当源画像就放 Redis，不做源层× 同介质两层没有意义；且丢失"回源成本"这个度量基准
5ms 不是拍脑袋
回源成本必须是"可感知的痛"：L1 命中 1μs vs 源 5ms 是 5000 倍差距——这个数量级让命中率的意义不言自明，也和业界口径一致（MySQL Buffer Pool 未命中的一次磁盘查询 5-10ms）。注入值进 config，M4/压测时可调。

决策二：特征字段由策略需求反推（不是先设计后使用）

// UserProfile —— 每个字段标注消费方, 无消费方的字段删除
public record UserProfile(
  String userId,
  MemberLevel memberLevel,       // M2: 高价值分层出价(1.5x)的依据
  boolean blacklisted,           // M2: 黑名单直接拒 + M0 断言的裁判依据
  long lastConvertTime,          // M2: "已购未满7d不参竞" —— M4 转化回流更新的目标字段
  int impressionCount7d,         // M2: 频控统计基础(用户×计划曝光数)
  long firstSeenTime             // 新用户冷启动识别(注册<3d 走保守策略)
) { }

生成规则进脚本：50 万用户按分布生成——会员 10%（VIP 3%）、黑名单 1%、最近 7 天内转化 5%、其余长尾。分布可复现（seed 固定），10% 用户故意不生成（模拟"合法但无画像"的长尾，供空值缓存场景使用——与 M0 的 10% 伪造 ID 区分：伪造=布隆拦截层，合法无画像=空值缓存层）。

验收预期

通过标准
  • 画像源服务独立端口可用，50 万用户可查，固定 seed 数据可复现
  • 延迟注入生效：单次查询 P99 ≈ 5ms + 抖动（注入 50ms 时 P99 相应抬升）
  • 特征字段与 M2 策略映射表成文：6 字段每个有消费方，无一"悬空字段"

坑速查表

症状原因处置
压测时源层不慢了延迟注入被 JIT 消除（Thread.sleep 不会，但若用忙等可能被优化）用 ScheduledExecutor/CompletableFuture.delayedExecutor 延迟返回，勿用忙等循环
画像分布失真（VIP 占比过高）生成脚本随机分布写错量级分布断言进冒烟脚本：抽查 1 万用户各维度占比 ±1% 内

02任务2 · L1 Caffeine + L2 Redis 两级缓存主体

要解决的问题问题驱动

三个层次的问题：① 为什么两级而不是一级——L2 Redis 每次命中也要一次网络 RTT（本地 ~1ms，跨机房更糟），3 万 QPS 下每秒 3 万次网络往返是纯浪费；L1 把热数据搬到进程内，微秒级零网络。② 为什么 L1 选 Caffeine——2026 年实证：大促场景 L1 命中率 92.5%，单热点 key 10 万 QPS 被本地层就地消化，对应 Redis 分片 CPU 从 98% 降到 18.5%。③ L1 容量给多少——不是拍脑袋，由 M0 的幂律分布反推。

决策一：本地缓存选型（对齐 2026 实证对比）

维度ConcurrentHashMapGuava CacheEhcache 3Caffeine（采用）
淘汰算法无近似 LRU多种可选W-TinyLFU（频率素描 + 三段式）
并发读高分段锁竞争偏重无锁读 + CAS
异步刷新不支持不支持有限refreshAfterWrite 原生
回源合并无同 key 串行有限LoadingCache 天然 singleflight
统计无基础丰富recordStats 完整
W-TinyLFU 为什么对 AdKernel 特别重要
通用缓存要防"扫描污染"（偶发批量查询把热点挤出去），而 AdKernel 的流量天然幂律（M0 埋的线）：热用户高频、长尾偶发。LRU 会被长尾用户稀释命中率，W-TinyLFU 用 Count-Min Sketch 记录访问频率，热用户稳如泰山——这正是"算法匹配流量分布"的选型叙事，比"Caffeine 性能好"高一个层次。

决策二：参数由数据反推，不是抄配置

Caffeine.newBuilder()
  .maximumSize(100_000)                    // = 50万 × 热头部20%(幂律), 内存≈20MB(10万条 × ~200B/条含条目开销)
  .refreshAfterWrite(Duration.ofSeconds(15)) // 异步刷新: 刷新期间旧值可读 —— stale 兜底的一半
  .expireAfterWrite(Duration.ofMinutes(10))  // 物理上限: 超过它连旧值都不可读
  .recordStats()                             // 命中率/驱逐/加载时长全量统计 —— M5 面板数据源
  .buildAsync(loader);                       // AsyncLoadingCache: 回源天然合并(见下)

// L2 Redis: TTL 随机偏移防雪崩(实证口径: 基础 5min + random 0~1min, 偏移 10%~20%)
// 两级 TTL 梯度: L1 15s刷新/10min过期, L2 5min —— 上层短、下层长, 上层兜下层的一致性
// 精确口径写进 ADR: 特征更新后最坏不一致窗口 = L1(10min) , 但 refreshAfterWrite
// 让 15s 后即开始拉新 —— 实际窗口以刷新节奏为准, 10min 只是"永不比这更陈旧"的上界

读路径与回源合并（Java 的天然优势）

CompletableFuture<UserProfile> get(String userId) {
  // L1: Caffeine 的 AsyncCache —— 同 key 并发未命中时, loader 只执行一次,
  //     其余请求共享同一 Future。Go 需要专门的 singleflight 库,
  //     Java 的 LoadingCache.get(key, loader) 内在语义就是 singleflight。
  return l1.get(userId, k -> {
    // L1 miss → L2: pipeline 化的 GET, 超时 3ms(预算的一半)
    UserProfile v = l2.get(k);
    if (v != null) return CompletableFuture.completedFuture(v);
    // L2 miss → 源(5ms 注入延迟) → 回填 L2(随机 TTL) → 返回
    return sourceService.load(k).thenApply(profile -> {
      l2.put(k, profile, ttlWithJitter());   // 写缓存失败不影响返回(实证纪律)
      return profile;
    });
  });
}
两条来自 2026 实证的生产纪律：① 写缓存失败不能让请求失败——回源成功但 L2 写入超时，直接返回数据，下一请求再试；② L2 反序列化失败静默回源——"缓存里的数据坏了"不该让请求失败，回源重拿一份即可。两条都是"为失败设计"的具体落点。

验收预期

通过标准
  • L1 命中率 ≥ 80%（幂律流量下稳态；预言数字 85% 的出处）
  • 延迟对比三组数字落盘：L1 命中 P99 < 0.1ms；L2 命中 P99 ≈ 1-2ms；回源 P99 ≈ 6-8ms（5ms 注入 + 开销）——特征查询总 P99 ≈ 2ms（80%+ 在 L1 消化）
  • 回源合并实证：冷启动 500 并发同 key 请求，源层实际收到 1 次查询（Caffeine 合并生效）

坑速查表

症状原因处置
L1 命中率远低于预期容量 < 热集大小，或流量分布不是幂律（M0 模拟器配置漂移）先查流量分布（Top20% 承载比），再调容量；容量翻倍做命中率曲线，找拐点
refreshAfterWrite 没生效感觉没配 executor，刷新挤占请求线程显式传自定义线程池；观察刷新任务队列积压指标
压测中 Full GC 频发L1 容量过大 + 画像对象逃逸（被业务代码长期持有引用）画像对象不可变（record 天然满足）；容量上限以堆内存 30% 为界反推

03任务3 · 防穿透双层（布隆 + 空值缓存）

要解决的问题问题驱动

2026 实证把三类缓存故障的根因分得很清（速览卡）：穿透是"查不存在的东西"、击穿是"一个热点瞬间失效"、雪崩是"大面积同时失效"——病根不同药方不同，一套方案包打天下必然顾此失彼。AdKernel 的穿透场景由 M0 模拟器埋好：10% 伪造 ID（恶意扫描/爬虫口径）。双层防线：布隆过滤器拦"一定不存在"，空值缓存兜布隆误判和"合法但无画像"用户。

决策：双层而不是单层

防线拦什么拦不住什么参数
布隆过滤器（前置）伪造 ID（说"不存在"≈100% 准确）误判"存在"（假阳性）50 万用户预热；fpp=0.01%（实证案例：大促布隆重构后误判率 0.0098%）
空值缓存（兜底）布隆误判的伪造 ID + 合法无画像用户—NULL 值短 TTL 30-60s（实证口径），不占长期内存
布隆的纪律
布隆说"不存在"一定不存在（前置拦截的性质来源），说"存在"可能不存在（假阳性）——所以它只能当第一道防线，永远不能当唯一防线。且布隆难删除、key 集合变化时要重建（实证案例用双缓冲位图无损热重构）——50 万用户固定集合是本场景适合布隆的前提，这个前提条件写进 ADR。

验收预期

通过标准
  • 穿透率 ≈ 0：稳态下源层收到的伪造 ID 查询 = 0（布隆拦截）+ 布隆误判被空值缓存吸收（唯一回源发生在首次误判，30-60s 窗口内一次）
  • 两层防线各有独立指标：布隆拦截率 ≈ 100%、空值缓存命中率可观测
  • 合法无画像用户返回默认画像（保守策略），决策不失败

坑速查表

症状原因处置
布隆内存暴涨fpp 设得过低（0.0001%）位图指数增长fpp 0.01% 即够（每 key ~1.2KB 总量级）；需求变了再调，别预优化
NULL 缓存把 L2 占满空值 TTL 太长 + 攻击者海量随机 IDNULL 独立 TTL（30-60s）；观测 NULL 占比，异常升高 → 触发风控口径（M3 限流接手）

04任务4 · 超时降级与 stale 兜底

要解决的问题问题驱动

低延迟系统的铁律（Spec 02 节）：宁可给保守决策，绝不超时。特征层的降级链：L2 超时 → 读 L1 旧值（stale）→ 默认画像（保守策略）。为什么允许读旧值：特征的不一致窗口本来就是预算过的（L1 15s 刷新节奏）——Redis 抖动 200ms 的场景里，读 15 秒前的画像和读最新画像，对"要不要参竞"这个决策的差异微乎其微；但超时一次就是一次媒体侧的默认处理，超时率超 1% 就触碰红线。用小的不一致换大可用，这笔账在 ADR 里算清楚。

降级链实现与注入实验设计

// 特征查询的软超时包装: 预算 3ms(L2)/5ms(总)
CompletableFuture<UserProfile> fet = getWithFallback(userId);
//  L2 路径: 3ms 超时 → catch TimeoutException → 读 L1 旧值(stale, 标记 degraded=stale)
//  L1 也没有(极端) → DEFAULT_PROFILE(保守: 不参竞/低出价, 标记 degraded=default)
// 每次降级必须: metrics.increment(degraded_stale / degraded_default) —— M5 告警数据源

// 注入实验(验收要件, 不是可选):
//   模拟器稳态 3000 QPS + 源层注入 50ms 延迟(模拟 DB 抖动) 5 分钟
//   → 预期: L1 命中的请求完全无感; 未命中请求走 stale; 决策超时率不升
//   再注入: L2 Redis 整体 hang 30s
//   → 预期: 全量走 stale/默认画像, 决策成功率不降, 超时率 0
stale 兜底的业界实证：巨量引擎特征服务公开口径——特征 RPC 超时后返回兜底缓存（12min 有效期），主链路永不因特征层失败而失败。我们的 L1 10min 物理过期 + 15s 刷新就是这个模式的自研版：旧值永远可读（10min 内），刷新永不停摆（15s 节奏），超时永远有出路（降级链）。

验收预期

通过标准
  • 两级注入实验通过：源 50ms 延迟 5 分钟 + Redis hang 30s，决策成功率 100%、超时率 0
  • 降级率可观测且分层：degraded_stale / degraded_default 两个独立计数，注入期曲线可回放
  • 降级语义正确性：stale 命中黑名单用户照样拒（旧值 ≠ 错值，15s 内的特征几乎总是对的）

坑速查表

症状原因处置
注入实验中超时率上升超时预算没有覆盖降级路径本身的耗时（读 L1 也要时间）降级路径预算单独核算：L2 3ms + L1 旧值读取 <0.1ms，总预算 4ms 内闭合
stale 读到"已过期物理 TTL"的值expireAfterWrite(10min) 到期后 Caffeine 直接删——旧值没了物理 TTL 是"旧值可读性"的上界，设计上它只兜 Redis 抖动（秒级），10min 绰绰有余；若要更长 stale 窗口需双 entry 方案（本场景不必，ADR 写明）
降级率统计不出来降级路径忘了打点M5 面板依赖这两计数——降级不观测 = 没降级

05速览卡 · 缓存三灾（面试高频，对照记忆）

类型根因（一句话）AdKernel 对应场景对策
穿透查"不存在"的数据，缓存永远不命中伪造 ID 攻击（M0 模拟器 10%）布隆前置拦截 + 空值缓存兜误判（30-60s）
击穿单个热点 key 恰好过期，瞬间流量全打源超级热用户特征过期瞬间回源合并（Caffeine 同 key 单 loader）+ refreshAfterWrite 异步刷新
雪崩大批 key 同时失效 / 缓存层宕机预热脚本统一写入统一 TTLTTL 随机偏移（10%-20%）+ L1 兜 L2 宕机 + 降级链

记忆锚点：穿透是"不存在"，击穿是"一个热的"，雪崩是"一批同时"——病根不同药方不同。2026 实证案例：某系统零点预热统一 30min TTL，零点三十分集体过期，DB 8 秒打满、P99 40ms→12s——"设过期时间本来为了安全，恰恰是安全措施造成故障"，TTL 随机偏移一行代码消灭之。

07速览卡 · 三级延迟账本（性能数字的溯源终点）

层级命中延迟容量角色
L1 CaffeineP99 < 0.1ms（微秒级）10 万条（热的 20%）消化 80%+ 流量；Redis 抖动时的兜底层
L2 RedisP99 ≈ 1-2ms（本地 RTT）近全量（TTL 5min+抖动）多实例共享层；回源挡板
源（画像服务）P99 ≈ 6-8ms（5ms 注入+开销）50 万全量广告主一方数据模拟；回源成本基准
加权总延迟P99 ≈ 2ms（80% L1 + 少量 L2）—对照基线：无缓存直查源 ≈ 12ms P99 —— 12ms→2ms 的两跳溯源到此为止

面试话术："特征查询 P99 从 12ms 到 2ms，不是我把哪个单点加速了 6 倍，而是 80% 的请求根本不再走网络——命中率才是低延迟的第一杠杆，单点优化是第二杠杆。"

08动态雷达 · 2026（M1 相关）

2026-09-28实证：电商大促多级缓存复盘——L1 Caffeine（W-TinyLFU + refreshAfterWrite 15s）就地消化 92,500 QPS（命中率 92.5%），Redis 分片 CPU 从 98% 红线回落 18.5%；布隆双缓冲重构后误判率 0.0098%；全链路命中率 99.88%，DB 回表仅 240 QPS。对项目的影响：两级缓存价值的最强量级证据；refreshAfterWrite 15s 参数出处；布隆 fpp 口径出处。
2026-10-13实战：SpringBoot+Caffeine+Redis 从设计到排坑——本地短过期+远端长过期+随机偏移、先写 DB 再删缓存、五大坑（穿透/击穿/雪崩/一致性/多实例同步）排查记录。对项目的影响：TTL 梯度设计（L1 短 L2 长）与随机偏移的工程依据。
2026-10-09深潜：Caffeine 从 W-TinyLFU 到多级一致性——Count-Min Sketch 频率素描原理、refreshAfterWrite 与 expireAfterWrite 语义区别、null 值穿透与空值包装。对项目的影响：参数语义辨析（"refresh 期间旧值可读"是 stale 兜底的实现基础）；选型对比表依据。
2026-10-16方法论：缓存三大问题工程化防护——三类故障根因严格区分（穿透=查不存在、击穿=单热点瞬间失效、雪崩=批量同时失效），防护矩阵分开设计；"没有演练过的防护，和没有一样"。对项目的影响：M1 验收全部以注入实验形式设计（注入 Redis 延迟/hang），防护必须演练。
2026-09-28工程细节：三级缓存的两个失效函数代价——L1 是"Redis 挂了还能撑住的那一层"（动机不是再快一点）；L2 反序列化失败静默回源（坏数据不让请求失败）；写缓存失败不影响返回；singleflight 按 key 合并。对项目的影响：三条生产纪律直接采纳进读路径设计。
2026-10-18案例：三马代驾缓存事故复盘——城市级 key 统一 TTL 早高峰集体过期，RT 30ms→900ms、连接池打满；按三类分治后回源量降 87%，"把 Redis 全停掉，核心接口只降级不宕机"。对项目的影响：降级链验收标准的口径——缓存层全挂时决策不失败，只降级。
