# AdKernel 广告域模型（domain.md）

> 版本：v1.0（M0 · 2026-10-19）
> 地位：**全项目术语宪法**。后续所有里程碑（M1–M5）、代码命名、协议文档、裁判断言均无歧义引用本表。
> 术语对齐 2026 年真实 RTA 生态：华为鲸鸿动能接口文档（HmacSha256/priceWeight/expId/transUniqueId）、腾讯 RTA&ADX 对接指引（超时率清退红线）、快手 ACQ 论文（账户五层层级）、百度投放侧实践（预算按计划分配）。

## 0. 层级图（一页画清）

```
广告主 Advertiser（一方数据持有者，系统的服务对象）
   │
   └── 计划 Campaign ★ AdKernel 唯一建模的管理层级
         ├── 日预算 Budget        （预算挂计划，不挂账户）
         ├── 策略规则 + 出价系数   （M2 策略引擎，按计划配置）
         ├── 人群定向              （黑名单/已购/高价值，M1 特征驱动）
         ├── 频控上限              （用户 × 计划 维度，M2 滑动窗口）
         └── （创意 Creative —— 名词保留，RTA 决策不消费，M0 不建模）
```

### 层级裁剪决策（对齐业界，不闭门造车）

| 方案 | 层级 | 判定 |
|---|---|---|
| 业界全层级（快手 ACQ 实证） | 广告主 → 账户 → 计划 → 单元 → 创意 | × 单元层承载关键词/创意变体管理，RTA 决策不消费单元信息，凭空多一层路由 |
| **AdKernel 裁剪后（采用）** | 广告主 → **计划** → （创意，名词保留） | ✓ 预算按计划分配、出价系数按计划策略计算——与投放侧实证一致："预算只能按计划分配" |

**为什么预算挂计划不挂账户**：计划是预算的独立控制单元。防超花（M3）因此天然是**计划维度**的——每个计划独立预扣/熔断，一个计划花爆不影响另一个计划。裁剪依据是数据流分析（RTA 决策消费哪些字段），不是偷懒。

## 1. 名词表（15 + 1 条，三段式）

> 阅读方式：每条名词三段——**定义**（一句话）、**为什么需要**（业务动机，写不出动机的名词就是不需要的）、**挂在哪层**（在 AdKernel 中的位置与里程碑归属）。

### 1. 广告主（Advertiser）

- **定义**：投放预算的出资方与一方数据（订单/会员/行为）的持有者，是整个系统的服务对象。
- **为什么需要**：系统里所有"替谁省钱"的问题都指向广告主——重复投放浪费的是他的预算，高价值用户加价赚的是他的增长。没有这个主体，"决策"就没了价值归属。
- **挂在哪层**：业务叙事的顶层；M0 单广告主模拟（电商平台），代码中不建模为运行时对象，仅在协议文档与实验报表中出现。

### 2. 用户（User / userId）

- **定义**：请求中携带的脱敏用户标识（模拟哈希 ID，对齐华为 oaid/ifa 脱敏传输口径），是特征查询与频控计数的主体。
- **为什么需要**：RTA 决策的粒度是"单次曝光机会 × 单个用户"——"已购即排除"排除的是用户，频控数的是用户 × 计划的曝光次数，特征服务查的是用户的画像。用户是全系统最细的业务主键。
- **挂在哪层**：决策请求字段 `userId`；M1 特征库主键（Redis 50 万用户画像）；M2 频控维度（用户 × 计划）；M4 归因回流的落点。

### 3. 广告计划（Campaign）

- **定义**：预算、策略、人群的独立控制单元，AdKernel 唯一建模的投放管理层级。
- **为什么需要**：所有投放控制旋钮都拧在计划这一层——日预算按计划分配（超花按计划隔离）、策略规则按计划配置、人群定向按计划圈选。没有计划的隔离，一个策略改坏会烧穿全部预算。
- **挂在哪层**：请求字段 `campaignId`；M0 单计划起步（cmp-001）；M2 多计划路由（请求按 campaignId 路由到独立预算/策略/人群，互不串扰）；M3 预算按计划独立预扣/熔断；账单与对账按计划聚合。

### 4. 广告位（AdSlot）

- **定义**：流量发生的媒体位置（信息流 feed / 开屏 splash），是场景的物理载体。
- **为什么需要**：不同位置的用户心智与转化意图完全不同——开屏强曝光适合品牌，信息流原生适合效果。它是场景化策略的输入：同一用户在开屏和信息流可以有不同的参竞意愿与出价系数。
- **挂在哪层**：请求字段 `adSlotId`（随 `scene` 联动生成：slot-feed-1001 / slot-splash-2001）；M2 场景化策略的分流依据。

### 5. 出价系数（bidRatio）

- **定义**：广告主对单次出价的动态调节因子，作用于媒体侧原始出价之上（对齐华为 priceWeight 字段）。
- **为什么需要**：RTA 的价值不止"要/不要"的二值筛选——高价值沉默用户 bidRatio 1.5 是"多花钱买确定性"，低价值用户 0.5 是"降价避险"。二值筛选浪费了信号强度，连续系数才能把一方数据的价值传导到竞价层。
- **挂在哪层**：响应字段 `bidRatio`，由策略引擎（M2）计算；预算引擎（M3）不感知（预算只问参不参竞，出价高低由媒体竞价结算）。M0 echo 恒返回 1.0。

### 6. 日预算（Budget）

- **定义**：计划的每日花费上限（自然日口径，跨零点重置），是"钱袋"。
- **为什么需要**：超花一分钱都是投放事故。预算是所有决策的最终约束——策略说得再天花乱坠，钱花完了就必须立刻停止参竞。它把"技术系统的决策"与"商业系统的责任"连接起来。
- **挂在哪层**：计划属性；M3 三级防线（请求前预扣滑动窗口 → 埋点后异步校正 → 超支熔断）+ pacing 匀速消耗 + 跨天重置（时钟边界测试）。M0 裁判预留断言："预算耗尽仍参竞 → 违规"（M3 接入后启用）。

### 7. 频控（Frequency Cap）

- **定义**：用户 × 计划维度的曝光次数上限（滑动窗口计数）。
- **为什么需要**：同一用户短期内反复看到同一广告，边际转化递减且伤害体验——预算效率和用户体验的双重约束。频控是"该拒的拒"在时间维度上的延伸：不仅拒掉已购用户，还要拒掉"看腻了"的用户。
- **挂在哪层**：计划属性（每计划不同上限，所以放策略层而非接入层——接入层只做通用防护，频控是业务规则）；M2 滑动窗口实现，频控命中率可观测。M0 裁判预留断言："频控超限仍参竞 → 违规"（M2 接入后启用）。

### 8. 曝光（Exposure）

- **定义**：转化漏斗第一层——竞价胜出后广告被展示给用户。
- **为什么需要**：漏斗与归因的起点。没有曝光事件，点击和转化就失去了"分母"和"时间锚点"——所有率指标（CTR/CVR/CPM）都以曝光为基数。
- **挂在哪层**：回传事件 `eventType=EXPOSURE`（媒体 → AdKernel）；M0 模拟器漏斗引擎产出（winRate 0.6 之后）；M4 归因链路的时间锚点；账单 impressions 字段。

### 9. 点击（Click）

- **定义**：漏斗第二层——用户对曝光广告的点击行为；**CPC 计费发生的地方**。
- **为什么需要**：钱花在这里。对账口径以此为准（自记消耗 = SUM(点击事件 cost)）——计费节点挂在点击而非曝光/转化，是本系统一切金额勾稽的基准。混淆计费节点是对账永远对不上的头号原因。
- **挂在哪层**：回传事件 `eventType=CLICK`（携带 `cost` 字段，CPC 金额）；M0 模拟器按 ctr 抽样产出；M3 对账的自记消耗源；M4 末次点击归因的依据事件。

### 10. 转化（Conversion）

- **定义**：漏斗第三层——用户完成广告主期望的行为（如下单）；归因的终点。
- **为什么需要**："已购即排除"的特征源——转化事件回流更新用户特征（最近转化时间），下次请求该用户即被排除。转化是数据飞轮的起点：没有转化回流，RTA 就退化回静态人群包。
- **挂在哪层**：回传事件 `eventType=CONVERT`；M0 模拟器按 cvr 抽样产出；M4 归因引擎的输入 + 特征近线回流（转化 → mini-MQ → 特征更新 → L2 失效，端到端 < 5s）。

### 11. 归因（Attribution）

- **定义**：转化功劳的分配——把一次转化归到哪个计划、哪个实验组的哪次点击上（AdKernel 采用**末次点击归因**，简化口径显式成文，ADR-0005）。
- **为什么需要**：技术优化 → 业务价值的翻译器。没有归因，就无法回答"RTA 组 CPA 比人群包组低多少"——所有投放决策都失去依据。归因口径本身就是产品决策（首次/末次/多点加权各有利弊），知道边界比堆功能成熟。
- **挂在哪层**：M4 归因引擎：转化事件按 requestId 反查 → 找到决策（末次点击口径）→ 归到计划/expId 分组；归因正确性校验脚本（抽样 1000 条，归属 100% 正确）。

### 12. 人群包（Audience Pack）

- **定义**：离线计算的用户名单（T+1 更新），传统投放的定向方式。
- **为什么需要**：**RTA 要取代的方案 = 对照实验的基线组**。没有人群包做对照，"RTA 有效"无从证明——它是被挑战的王者，不是被遗忘的旧物。人群包的缺陷（T+1 滞后导致已购用户次日仍被投放）正是本项目的业务初心。
- **挂在哪层**：M4 对照实验：基线组用静态人群包决策、实验组用完整 RTA 链路，同一套漏斗概率，报表对比 CPA/参竞质量/预算利用率。

### 13. 实验分桶（Bucket / expId）

- **定义**：AB 分流的最小单元——按一致性哈希把用户稳定地映射到某桶（同用户同桶），桶归属通过响应字段 `expId` 透传。
- **为什么需要**：同用户同桶 = 决策稳定性 + 归因可比。`expId` 闭环是协议层最重要的设计：广告主在响应里告诉媒体"这次决策属于哪组"→ 媒体回传事件时原样带回 → 归因按 expId 分组——**媒体的实验分组必须广告主自己透传，媒体不会替你记**（华为 expId 字段实证）。
- **挂在哪层**：响应字段 `expId` → 回传事件字段 `expId` → M4 归因分组 + AB 报表；M2 策略发布灰度复用同一分流（新策略先放 5% 流量，ADR-0008——一次建设两处受益）；分流稳定性 100%、分组流量比 < 1% 偏差。

### 14. pacing（匀速消耗）

- **定义**：预算消耗的时间分配策略——按时间片把日预算切成小额额度，匀速释放而非前松后紧。
- **为什么需要**：防挤兑。预算不做 pacing 时，早盘豪掷耗尽预算，午后的优质流量无钱可投（媒体侧"防超投防挤兑"同款问题，巨量引擎实证）。pacing 把"花得完"升级为"花得匀"。
- **挂在哪层**：M3 pacing 模块：按时间片分配额度，消耗曲线平缓 vs 不做 pacing 的前松后紧对照曲线；验收看曲线形状而非单一数字。

### 15. 对账（Reconciliation）

- **定义**：T+1 比对媒体账单与自记消耗（按 requestId 级明细），差异定位到根因的流程。
- **为什么需要**：信任的最后一道兜底。计费对不上是广告系统 P0 事故——预算防线做得再密，没有对账就不知道"防没防住"。对账不是技术组件，是商业信任机制（引用 mini-MQ 的零丢失实证背书）。
- **挂在哪层**：M3 对账模块：四桶分类（账单有自记无 / 自记有账单无 / 金额不一致 / 重复计费）+ 差异定位流程成文（归属窗口/去重口径）；验收：账单差异 = 0，人为注入差异能定位根因。

### 16. 超时率（Timeout Rate）

- **定义**：RTA 响应超时次数占总请求数的比例（媒体侧口径，超时阈值 60ms）。
- **为什么需要**：RTA 的**生存指标**——不是"慢一点没关系"，腾讯对接指引明确"超时率或错误率大于 5%，警告后 7 天未解决 → 冻结请求"。超时的后果是媒体按默认策略处理 + 商务层面被清退。它把延迟优化从技术偏好升级为合同级义务。
- **挂在哪层**：M0 模拟器裁判断言（> 60ms 记超时；超时率 > 1% 报告标红——对齐腾讯 5% 红线留 5 倍安全边际）；M5 可观测面板的 P0 级告警规则。
