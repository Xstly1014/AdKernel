AdKernel · M0 深入手册

地基里程碑：15 个名词、3 份协议、1 个严格对手方、1 条会呼吸的闭环。M0 结束时：媒体模拟器能以 1 万+ QPS 向 RTA echo 服务发流量、按概率漏斗回传曝光/点击/转化、生成模拟账单——整条业务链路的数据骨架先于一切优化存在。本册所有设计决策对齐 2026 年真实 RTA 生态（华为公开接口文档、腾讯对接指引、快手/巨量层级口径），不是想象出来的玩具协议。

00M0 的定位与伏笔

为什么第一册不做决策、先做名词和对手方问题驱动

三个理由：① 消歧义是并行开发的前提——"计划""单元""创意"在业界有严格层级（快手 ACQ 论文实证：advertiser → account → campaign → unit → creative），自造术语会在 M2 多计划路由时埋下混乱；② 对手方先行 = 验收先于实现——媒体模拟器是 ADR-0001 定下的"流量生成 + 业务合法性断言 + 转化回传/账单"三合一角色，它先存在，后面每个里程碑的代码一写完就立刻被它拷问；③ requestId 贯穿设计必须 M0 定死——归因引擎（M4）的实现基础是"决策请求与回传事件用同一 requestId 串联"，这条线在协议里断了，后面无法补。

本册埋的伏笔（后续哪里收）

M0 埋的线在哪收
用户流量服从幂律分布（热头部 + 长尾）M1：L1 缓存命中率 85% 的预言直接依赖这个分布——均匀分布会让缓存优化失去意义
QPS 曲线含洪峰时段M3：限流与 pacing 的压测场景
响应含 expId（实验组透传）M4：归因分组 + AB 报表的分组依据——华为真实接口实证字段
回传事件含 cost（点击计费）M3：对账的数据源（自记消耗）
断言：超时率红线M5：可观测面板的超时率告警——腾讯清退标准（>5% 冻结）是业务口径
延迟基线 JSONL 落盘M1/M5：一切优化的对照基线

01任务1 · 广告域 15 名词表

要解决的问题问题驱动

为什么不直接开写代码？因为广告系统是术语密集型业务——你已有的手册里"计划"出现过无数次，但"计划"和"单元"什么关系、"预算"挂在哪一层、"出价"和"出价系数"是不是一回事，这些不提前钉死，M2 的多计划路由就会写出串预算的 bug。业界有现成层级口径（快手 ACQ 论文的五层结构、华为鲸鸿动能的三层管理），对齐业界而不是自造，面试官一听术语就知道你研究过真实系统。

决策矩阵：层级怎么裁剪

方案内容判定
全层级（业界）广告主 → 账户 → 计划 → 单元 → 创意× 单元层（承载关键词/创意变体）对 RTA 决策无独立作用，凭空增加一层路由
裁剪后（采用）广告主 → 计划（预算/策略/人群的独立控制单元）→ 创意（仅名词保留，响应字段可选）✓ 预算按计划分配、出价系数按计划策略计算——与百度投放侧实证口径一致："预算只能按计划分配"
为什么预算挂计划不挂账户
投放侧实证（2026-10 百度账户结构文章）："预算只能按计划分配，出价只能按单元设置"——计划是预算的独立控制单元。我们的防超花（M3）因此天然是计划维度的：每个计划独立预扣/熔断，一个计划花爆不影响另一个计划。这个裁剪在面试里是加分项："我裁掉了单元层，因为 RTA 决策不消费单元信息——裁剪依据是数据流分析，不是偷懒。"

执行：docs/domain.md 规格

15 个名词，每个名词三段：定义一句话、为什么需要它（业务动机）、在 AdKernel 里挂在哪层。完整表格见速览卡，两个示范条目：

## 出价系数（bidRatio）
定义: 广告主对单次出价的动态调节因子, 作用于媒体侧原始出价之上。
为什么需要: RTA 的价值不止"要/不要"的二值筛选——高价值沉默用户 bidRatio 1.5
  是"多花钱买确定性", 低价值用户 0.5 是"降价避险"。二值筛选浪费了信号强度。
挂在: 响应字段, 由策略引擎（M2）计算, 预算引擎（M3）不感知。

## 超时率（timeout rate）
定义: RTA 响应超时次数占总请求数的比例。
为什么需要: RTA 的生存指标——不是"慢一点没关系", 腾讯对接指引明确
  "超时率或错误率大于 5%, 警告后 7 天未解决 → 冻结请求"。
  超时的后果是媒体按默认策略处理 + 商务层面被清退。
挂在: M0 模拟器统计, M5 告警规则（红线告警值 1%, 预留安全边际）。

验收预期

通过标准
  • 15 个名词三段俱全，术语与业界对齐（campaign/bidRatio/expId 等英文名可用）
  • 层级图一页画清：广告主 → 计划 → （创意，名词保留），预算挂计划
  • 自检：随机挑 3 个名词，能不看文档讲出"为什么需要它"

症状原因处置

02任务2 · 三份协议

要解决的问题问题驱动

协议是系统的宪法，M4 归因、M3 对账、M2 灰度的实现自由度全在这里被限定。核心设计只有一条主线：requestId 贯穿——决策请求、曝光、点击、转化、账单五类记录用同一 requestId 串联，这是末次点击归因、幂等去重、对账定位三条链路的共同钥匙（华为真实接口的 transUniqueId 字段就是这个用途的实证）。

决策一：字段对齐业界实证，不闭门造车

// ① RTA 决策请求（媒体 → AdKernel）      对齐: 华为鲸鸿动能 RTA 接口文档(2026-07)
{ "requestId": "req-8f3a…",          // 全链路贯穿 ID = 归因的钥匙
  "requestTime": 1763011200000,
  "campaignId": "cmp-001",
  "userId": "u-hash-7c2e…",           // 模拟哈希 ID(华为: oaid/ifa 脱敏传输)
  "adSlotId": "slot-feed-1001",       // 广告位(feed/开屏)
  "scene": "feed",                   // 场景, 影响策略
  "sign": "hmac…" }                  // 鉴权: HmacSha256(requestId+requestTime+userId, secretKey)

// ② RTA 决策响应（AdKernel → 媒体）
{ "code": 0,                         // 0 正常; 限流/降级用专用码(M3 伏笔)
  "target": true,                    // 是否参竞
  "bidRatio": 1.5,                   // 出价系数(华为 priceWeight 实证字段)
  "expId": "exp-01-bucketA",         // 实验组透传!(华为 expId 实证) —— M4 归因分组依据
  "reason": "high_value_silent" }    // 决策原因码: 调试 + M4 归因细分的素材

// ③ 转化回传（媒体 → AdKernel，漏斗逐级上报）
{ "requestId": "req-8f3a…",         // ← 与决策请求同一 ID —— 贯穿设计
  "eventType": "CLICK",             // EXPOSURE / CLICK / CONVERT
  "eventTime": 1763011203120,
  "campaignId": "cmp-001",
  "expId": "exp-01-bucketA",        // ← 响应里的分组被媒体原样带回
  "cost": 0.7 }                      // 点击计费金额(CPC) —— M3 对账的自记消耗源

// ④ 模拟账单（T+1 日级文件，媒体侧生成）
{ "date": "2026-10-18", "campaignId": "cmp-001",
  "totalCost": 12345.67, "impressions": 987654, "clicks": 19753 }
expId 闭环是本册最重要的协议设计
AdKernel 在响应里告诉媒体"这次决策属于实验组 bucketA"→ 媒体回传事件时原样带回 → 归因引擎按 expId 分组统计 CPA → AB 报表。这条字段不设计，M4 的 AB 实验就要另建分组通道。业界真实接口（华为 expId 字段）证明这不是过度设计——广告主的实验分组必须自己透传，媒体不会替你记。

决策二：鉴权用 HmacSha256 签名（对齐华为）

sign = HmacSha256(requestId + requestTime + userId, secretKey)。为什么不是简单 API Key：签名覆盖了请求体关键字段，防篡改 + 防重放（requestTime 参与签名，过期签名直接拒）。M0 的模拟器与 echo 服务共享 secretKey 即可，实现成本约 20 行。

验收预期

通过标准
  • 三份协议（决策请求/响应、转化回传、模拟账单）成文：docs/protocol/*.md，各带样例 JSON
  • requestId 五类记录贯穿可追溯：手工构造一条请求，其曝光/点击/转化回传能被同一 ID 串起
  • 鉴权：篡改签名 → 401；过期时间戳 → 401

坑速查表

症状原因处置
回传事件里没有 expId协议设计时觉得"媒体怎么会知道我的实验组"就是响应里带过去、媒体带回来——自证闭环。M4 归因断链的最大隐患，M0 必须锁死
cost 只在转化事件里带混淆计费节点CPC 计费挂在点击事件上（曝光/点击/转化三层漏斗，花钱在点击）；M3 对账口径以此为准
requestId 用自增整数图省事必须随机 UUID/雪花——自增可预测，M3 对账幂等去重（桶③重复计费）和分布式部署都会踩

03任务3 · 媒体模拟器（严格对手方）

要解决的问题问题驱动

ADR-0001 已定：JMeter/wrk 只会发流量，不会校验业务合法性，也不会产生回流数据。模拟器承担三个角色：流量生产者（真实分布）、裁判（断言违规）、数据源（漏斗回传 + 账单）。它先于 RTA 服务存在——裁判先于运动员是验收式开发的纪律。

决策一：技术选型

方案优势劣势判定
Java 21 虚拟线程 + HttpClient（采用）每请求一个虚拟线程，代码直写同步逻辑；单机 1 万+ QPS 轻松达成吞吐上限低于 Netty（约 5-10 万级）✓ M0 echo 阶段瓶颈不在客户端；上限足够用到 M5 压测（届时可切 Netty 生成器）
Netty 异步客户端吞吐上限极高回调/事件驱动复杂度，模拟器写起来比被测服务还难× 优先级错了：模拟器要的是"可信"，不是"快"
JMeter + 自定义断言插件现成 UI无法实现漏斗回传/账单生成；断言表达能力弱× ADR-0001 已否决

决策二：流量分布——幂律，不是均匀

用户流量按幂律分布（Zipf，s≈1）：20% 热用户承载约 80% 流量。这不是学术洁癖——M1 缓存命中率的全部意义建立在热用户存在的前提上：均匀分布下任何局部缓存都约等于全量缓存，命中率优化的叙事直接作废。真实媒体流量天然头部集中（活跃用户反复请求），模拟器必须复现这一点。

// 用户抽取: Zipf 采样 + 少量伪造 ID（10%, M1 防穿透的靶子）
// QPS 曲线: 可配置 shape —— 平峰 3000 → 晚高峰 8000 → 洪峰 spike 15000（持续 30s）
// 场景分布: feed 70% / splash 30%（开屏）—— M2 场景化策略的输入

决策三：断言清单（裁判的判罚规则）

断言违规判定依据
黑名单用户参竞target=true → 记违规策略语义正确性（M2 前用静态名单校验）
响应超 60ms记超时（按媒体默认策略处理）主流媒体 60-100ms 硬限（2026 综述口径）
超时率 > 1%（红线告警）裁判报告标红腾讯清退红线 5%（我们留 5 倍安全边际）
协议字段缺失/非法记错误契约测试基础
验签失败记错误鉴权正确性
超时率不是技术指标，是生存指标——腾讯 RTA 对接指引（2025-11 更新）原文："客户 RTA 超时率或错误率大于 5%，且警告后 7 天内仍未解决的……直接冻结客户 RTA 请求。"M0 把这条红线写进裁判，M5 的告警规则就有了业务出处，面试讲"为什么 P99 这么重要"时，答案是合同级的。

验收预期

通过标准
  • 稳定输出 1 万+ QPS（洪峰模式 1.5 万），持续 ≥5 分钟，报告延迟分布（P50/P99）
  • 断言生效实证：echo 服务故意插入黑名单用户仍返回参竞 → 裁判报告出现违规记录
  • 流量分布验证：抽样统计 Top20% 用户承载流量占比 ≈ 80%

坑速查表

症状原因处置
模拟器自己先打满 CPU，QPS 上不去JSON 序列化/验签在热循环里重复创建对象复用 ObjectMapper 实例；验签开关分级（M0 压测档可关）；监控模拟器自身 CPU（裁判不能先累死）
洪峰 spike 期延迟数据失真连接池打满，排队时间混进统计 HttpClient 连接池参数显式配置并记录口径；洪峰数据单独分桶统计
Windows 环境端口耗尽1 万 QPS 临时端口回收慢长连接复用（keep-alive）；TIME_WAIT 观察项写进 docs

04任务4 · echo 骨架与转化漏斗

要解决的问题问题驱动

echo（恒参竞）的意义不是"写个 Hello World"：① 打通全链路数据骨架——请求→决策→按漏斗概率回传→账单文件生成，M0 结束时闭环每一段管道都是通的，后面五个里程碑只是往管道里换更好的零件；② 落盘延迟基线——未来一切"优化了 X ms"都对照这组数字。

决策：漏斗概率参数化（不是拍脑袋常量）

// 转化漏斗(模拟器侧): 参竞决策 → 竞价胜出 → 曝光 → 点击 → 转化
winRate    = 0.6     // 竞价胜出率(简化: 不模拟真实竞价, M5 归因说明裁剪)
ctr        = 0.02    // 点击率: 信息流行业基准 1%-3%
cvr        = 0.03    // 转化率: 电商行业基准 1%-5%
// 三者进 config/funnel.yaml —— M4 对照实验的"调节旋钮":
//   基线组与实验组的差异由策略真实决策产生, 而不是漏斗概率作弊
为什么漏斗必须参数化
M4 的对照实验要证明"RTA 决策质量高于人群包"：两组走同一套漏斗概率，唯一变量是决策逻辑——实验组排除已购用户后，其曝光→点击→转化的样本质量自然变化，报表差异才可归因于决策本身。概率若硬编码，实验就调不了；若两组概率不同，就是作弊。

执行清单

步骤产出
1. echo 服务：Spring Boot（或裸 HttpServer）+ HmacSha256 验签 + 协议校验，决策恒 target=true、bidRatio=1.0决策 API 可用，签名防伪生效
2. 模拟器漏斗引擎：参竞响应 → 按 winRate 模拟胜出 → 曝光事件 → 按 ctr 抽样点击 → 按 cvr 抽样转化，三类事件按协议回传回传事件流生成，requestId 贯穿可查
3. 账单生成器：日终汇总回传 cost → 账单文件模拟账单文件（M3 对账的对手方数据）
4. 全链路冒烟：5 分钟 3000 QPS 平峰 → 检查五类记录数量勾稽（曝光 ≥ 点击 ≥ 转化）漏斗数量自洽报告
5. 延迟基线落盘：每秒一行 JSONL（ts/qps/p50/p99/errRate/timeoutRate）baseline-m0.jsonl——M1/M5 对照基线

验收预期

通过标准
  • 全链路闭环：任选一条 requestId，五类记录（请求/响应/曝光/点击或转化/账单归属）可串联追查
  • 漏斗勾稽：曝光数 > 点击数 > 转化数，比例符合配置概率（±3% 统计误差内）
  • 延迟基线落盘：echo 全链路 P99 记录在案（预期个位数 ms——这是未来 38ms 预言的"地板"）

坑速查表

症状原因处置
点击数 ≥ 曝光数漏斗抽样逻辑写反（先抽点击再判曝光）漏斗必须逐级递减校验；加一条断言进冒烟脚本
回传事件丢失 requestId 关联异步回传时上下文没带上回传任务构造时就闭包捕获 requestId——不要在回传时重新生成
echo P99 反而波动大JIT 未预热 / GC 停顿混入复用 M5 纪律（预热丢弃、3 轮取中位）——基线的口径从 M0 就统一

07速览卡 · requestId 贯穿（全系统主键）

要点内容
是什么每次决策请求的 UUID，被响应、曝光、点击、转化、账单明细五类记录共同携带
为什么关键三条链路的共同钥匙：归因（M4 末次点击：转化事件反查 requestId → 找到决策）、幂等（M3 对账桶③：重复回传按同 ID 去重）、对账（M3：自记消耗与账单明细按 ID 级比对）
业界实证华为 RTA 接口的 transUniqueId 字段——"关联 id，用于与点击回传进行关联"，同一设计思想
实现纪律回传事件构造时闭包捕获，禁止重新生成；全局禁止把 requestId 当业务主键以外用途（如排序依据）
面试话术"我的归因、幂等、对账三条链路共用一个贯穿 ID——设计协议时我把它当宪法第一条"

08动态雷达 · 2026（M0 相关）

2026-07-22实证：华为鲸鸿动能 RTA 接口文档（公开）——真实媒体侧 RTA 协议字段全表：HmacSha256(requestId+requestTime+oaid) 鉴权、priceWeight 出价比例、expId 实验 ID 透传、transUniqueId 点击回传关联、oaid 脱敏传输。对项目的影响：本册协议字段与鉴权设计的直接依据——协议不是想象的，是对齐真实接口的。
2025-11-07实证：腾讯营销 RTA&ADX 对接指引——准入门槛（RTA 日均消耗 10 万）、质量清退标准（超时率/错误率 >5% 警告 7 天未解决 → 冻结请求）、标准套餐 QPS 上限 30 万。对项目的影响：断言清单的红线值有了业务出处；"超时是生存指标"从口号变成合同条款。
2026方案：广告平台之 RTA 系统设计（头条/火山）——低延迟分层预算（网关 ≤50ms、引擎 ≤30ms）、全链路内存化、请求合并、监控口径（P50≤10ms / P99≤30ms / 错误率 ≤0.1% / 超时率 ≤0.01%）。对项目的影响：02 节延迟预算分解的对照系——我们的 50ms P99 目标在业界口径的"宽松档"，预期管理有依据。
2026-08-21学术：快手 ACQ 论文（arXiv 2412.06167v2）——广告账户五层层级结构实证（advertiser → account → campaign → unit → creative），投放管理的最小控制单元是 campaign。对项目的影响：任务1 层级裁剪的依据——裁掉 unit/creative 管理层，保留 campaign 为预算/策略控制单元。
2026-10-13投放侧：百度广告账户搭建顺序（实践文章）——"结构定边界、预算定空间、定向定范围、出价定节奏"；预算只能按计划分配；已转化人群重复投放是纯浪费。对项目的影响：业务初心的投放侧印证——AdKernel 的价值主张（已购排除/差异化出价）与一线投放痛点逐字吻合。
2026-07-15实证：华为鲸鸿动能账户结构文档——计划/任务/创意三层管理、日预算控制、计费方式 CPC/CPM/CPA/oCPC。对项目的影响：漏斗计费口径（CPC 花在点击层）与日预算概念的行业定义。
