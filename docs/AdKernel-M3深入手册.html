M3 · 限流、预算、对账与降级总开关

AdKernel 里程碑三 —— M2 是油门（会精细化花钱），M3 是刹车（花不超）、仪表盘（花得明白）和断电开关（出事能停）。

00总纲与伏笔收线

M2 结束时，AdKernel 已经能对每一次决策做出「参不参竞、出价多少」的精细化判断。但一个只会踩油门的系统是不完整的：决策在先、扣费在后的 RTA 时序天然带着超花风险；没有任何保护的决策接口在流量突增时会被打挂；钱花完了没有审计就无法证明系统没有撒谎。M3 的四个关键词——限流保护自己、预算防超花、对账证明清白、总开关一键断电——补上「花钱纪律」这最后一块业务拼图。

M3 与简历数字的对应关系（resume0.2.tex 第二条 bullet 溯源）：「预算控制与对账：三级防线+pacing、超支<1.5%、T+1 对账清零」——三个数字全部在 M3 交付：三级防线+pacing = 任务 2；超支<1.5% = 任务 2 验收指标；T+1 对账清零 = 任务 4 验收指标。

01任务1 · QPS 限流：决策接口的自我保护

问题驱动为什么决策接口必须有限流

M1 的多级缓存让 P99 停在 2ms，M2 的策略引擎让决策精细化——但这一切的前提是流量在系统承载范围内。两个现实场景会把 AdKernel 打挂：

  • 流量突增：媒体侧运营活动导致请求量翻 3 倍，未命中缓存的请求全部穿透到画像源（M1 的 L2 降级链再深也架不住源被打穿），60ms 延迟预算全线击穿，媒体侧超时率超 5% 触发清退红线（M0 的腾讯清退红线）——限流缺失的代价不是报错，是被媒体清退；
  • 重试风暴：媒体侧超时重试，超时请求和重试请求叠加，系统在过载边缘被重试流量推入雪崩。

决策矩阵：四种算法选型

算法原理关键缺陷 / 特性适用
固定窗口计数窗口内计数、超限拒绝、到点清零临界突刺：0.9s 处 100 个 + 1.1s 处 100 个 = 2 秒内放行 200 个（2 倍突发）粗粒度、对边界不敏感
滑动窗口窗口细分小格滑动统计平滑但占内存高精确限流
漏桶恒定速率流出严格匀速、不允许任何突发流量整形、保护脆弱下游
令牌桶 ✓匀速放令牌、桶内可积攒允许可控突发、长期平均限速API 限流标准选择
选型口诀（动态雷达实证）：「限自己的系统用令牌桶（容忍突发），限别人的系统用漏桶（保护下游）」。AdKernel 是被调方——媒体调我们，我们保护自己，选令牌桶。我们的输出只是纯计算后的响应报文，没有需要整形的下游写操作，漏桶无用武之地。

单机还是分布式

方案原理取舍
Guava RateLimiter（单机）JVM 内令牌桶零网络开销；多实例下各自计数，总量对不上（N 实例 = N 倍限额）
Redis + Lua 中心化全局共享桶、Lua 原子读判写精确；每次请求多一次 Redis 往返（决策链路上加 1-2ms）
配额分片全局配额 ÷ 实例数，各限各的零网络开销；流量不均时实例配额浪费或超限

AdKernel 决策：单实例部署起步，入口用 Guava RateLimiter（预热模式），但把限流值与限流器实例封装在 RateLimitGate 接口之后——未来多实例化时替换为「Redis + Lua + 本地预扣减」实现，业务代码零改动。这是把「单机够用」和「面试要讲分布式」同时拿下的做法：接口先行，实现可演进。

执行：三个工程要点

1. 惰性时间推算（Lazy Refill），不要定时器

不要起后台线程每 1/rate 秒往桶里放一个令牌——请求到达时刻用时间差一次性补算：

/**
 * 令牌桶核心：读时间差 → 补令牌 → 判断 → 扣减。
 * 惰性推算：无定时线程，无空转开销，成千上万条限流规则也扛得住。
 * Guava RateLimiter 内部即此模型，这里手写版用于叙事，生产直接用 Guava。
 */
boolean tryAcquire(long nowMs) {
    long elapsed = Math.max(0, nowMs - lastRefillMs);
    tokens = Math.min(capacity, tokens + elapsed * rate / 1000); // 补令牌，封顶
    lastRefillMs = nowMs;
    if (tokens >= 1) { tokens -= 1; return true; }
    return false;
}

2. 预热（Warmup）

冷启动时桶是满的，开闸瞬间大流量全量涌入，会把还在 JIT 预热、缓存未填的系统和下游直接打穿。Guava 的 RateLimiter.create(rate, warmupDuration) 让令牌生成速率从低到高爬升——限流器自己也要热身。

3. 被限流之后返回什么：noBid，不是 429

普通接口限流与广告接口限流的本质区别：普通接口超限返回 429 + Retry-After；RTA 决策接口超限返回的是 noBid（不参竞）——这是 M0 协议里天然存在的合法响应。被限流的请求不是「报错」，而是「这次生意我不做」。妙处有三：①媒体不会重试风暴（noBid 是正常响应不是失败）；②不参竞就不会赢、不会花钱，限流的代价是少赚钱，不是故障；③对账口径天然一致（M0 断言清单：被拒请求必须在账单中缺席——限流与断言直接联动，模拟器可验证限流真的生效了）。

限流三件套（缺一件就是没测试过的保险丝）

  • 降级联动：限流触发后的响应（noBid + reason=RATE_LIMITED）——reason 码继续全链路打点（M2 起的规矩）；
  • 动态配置：限流值不写死，放配置（M2 热更新同款机制：文件 watch + 原子切换），压测与大促口径不同；
  • 监控三指标：限流触发 QPS、触发后拒绝率、触发时段分布——限流频繁触发说明容量规划要重估，是告警不是常态。

验收预期

  • 压测流量 1.5 倍于限流值：放行 QPS 稳定在限流值 ±5%，被拒请求平均 RT < 1ms（快速失败，不占下游资源）；
  • 限流期间正常放行请求 P99 不劣化（保护有效性：过载时服务质量不滑坡）；
  • 模拟器断言：被拒请求（reason=RATE_LIMITED）在曝光/账单中 100% 缺席。

02任务2 · 预算三级防线与 pacing：防超花

问题驱动RTA 预算控制的本质难题

先把时序摆出来，这是整个任务 2 的根基：

决策(此时承诺出价，钱还没花)
  → 媒体竞价(用我们的 bidRatio)
    → 赢了(曝光即将发生——CPC 下曝光本身不扣费，但点击随时可能来)
      → 曝光发生(已展示，钱仍未花——计费点在点击)
        → 点击发生(钱确定花了——CPC，M0 协议口径)
          → 点击回传到达(我们才确切知道花了多少)

检查预算的时刻（决策）永远早于确切知道花费的时刻（回传）。这两点之间所有已参竞的流量都无法撤回——这就是超花窗口（money in flight）。不设计防线的结果：日预算 10 万的计划，零点后 1 小时被幂律头部流量打爆，媒体账单 13 万，广告主投诉。超花不是 bug，是 RTA 时序的固有属性，只能对冲，不能消灭。

决策：三级防线设计

防线时机动作性质
L1 预扣决策时（同步）决策通过即按估计成本预扣：estCost = bid × winRate × ctr（CPC：赢了且被点击才扣费；winRate/ctr 均为 M0 funnel.yaml 参数，在此复用）乐观估计，低延迟，误差大
L2 实扣修正点击回传时（异步，CPC 计费点）按回传携带的真实金额修正账本：先冲销该决策的预扣，再入账真实花费（Lua 原子，M2 频控同款论据）精确对齐媒体账单口径
L3 硬阈值拒绝决策时（同步）剩余预算 < 安全垫（如日预算 5%）→ 直接 noBid，不再进入策略引擎兜底：宁可少花，不可超花
三级防线的面试一句话：L1 用估计值快速挡住大流量（误差换延迟），L2 用真实值持续纠偏（账本逐渐逼近媒体口径），L3 保证无论估计多离谱、回传多滞后，最后一分钱都有人看着。超支率 = 在飞窗口花费 + L1 估计误差，三级防线把这两项共同压在 1.5% 以内。

顺序有讲究：L3 检查放在 L1 之前、且放在策略引擎执行之前（预算不足就别浪费 CPU 算策略了——快速失败原则贯穿 M2/M3 一致）。

pacing：为什么不能让预算「上午烧完」

预算防超花只解决了「花不超」，没解决「花得匀」。M0 模拟器的流量是幂律分布（Top 20% 用户承载 80% 流量），叠加人群包定向后，头部时段消耗会远超均值——没有 pacing，日预算会在上午 10 点烧完，下午的优质流量（M4 实验将证明晚间转化率更高）一分钱都花不到。pacing 的业务本质：同样一笔预算，花在什么时刻是有效率的差别。

目标轨迹线（Xandr Daily Pacing 思想裁剪）

目标消耗(t) = 日预算 × 可投放分钟数已过占比
              （对齐投放时段；无时段限制 = 1440 分钟全天）

每个 pacing 周期（15 分钟，对齐 Xandr 实证周期）：
  偏差 = 实际消耗 - 目标消耗
  偏差 > +容差 → 收紧参竞（降低出价系数 / 概率性跳过流量）
  偏差 < -容差 → 放开参竞（恢复系数）

追赶必须有上限（Xandr 文档明确警告的 spend spike 尾部风险：晚间为追回欠账全放开，最后 30 分钟预算脉冲烧穿）——追赶速率封顶，宁可欠账过夜，不可尾部爆冲。

工程实现：pacing 格子（离散化）

不实现连续调节器，用更笨但更可解释的方案——把全天切成 5 分钟一格的预算格子（288 格），每格持有当日预算的 1/288（可按流量分时曲线加权，M0 漏斗参数化同款思路）。格子内预算耗尽 → 本格内概率性跳过；格子结束 → 剩余滚入下一格。优点：每分钱都能回答「属于哪个格子的账」，对账（任务 4）多了一层明细口径，pacing 曲线可直接画成监控面板。

Safety Budget 裁剪（Xandr 实证 → 我们的红线）

Xandr 建议 safety budget 设为日预算 5-10 倍 + 80% 处自动告警。5-10 倍是大型投放生态（多时区、多 bidder、回传延迟不可控）的宽容度；AdKernel 单时区、单实例、回传延迟由模拟器控制，裁剪为硬上限 1.1 倍日预算 + 80% 告警——80% 告警点直接采纳（业界共识），倍数按自身架构收紧，这也是「参数裁剪要有理由，不是照抄」的叙事素材。

执行：预算账本关键结构

/**
 * BudgetLedger：每计划一本账（M2 CampaignContext 已预留挂点）。
 * 金额一律用「分」为单位的 long —— 浮点累计误差是对账头号敌人（任务4坑表）。
 */
record BudgetState(
    long dailyBudgetCent,        // 日预算（分）
    long reservedCent,           // L1 预扣在途（决策加、回传冲销）
    long spentCent,              // L2 实扣已花
    long hardCapCent,            // L3 硬上限 = dailyBudget × 1.1
    String budgetDate            // 归属日 yyyyMMdd —— 任务3 的主角
) { }

// L1 预扣（决策路径，须与频控一样原子 —— 同一 Lua 家族）
// estCost = bid × winRate × ctr（CPC：赢且被点击才扣费），均来自 funnel.yaml；预扣失败 → noBid(reason=BUDGET_EXHAUSTED)
// L2 冲销+实扣（回传路径，Lua 原子）：
//   spent += realCost;  reserved -= estCostOfThisRequest;
//   requestId → estCost 的映射在决策时写入，回传时凭 requestId 反查（M0 requestId 贯穿再次发力）

验收预期

  • 正常日：超支率（实扣 - 日预算）/ 日预算 < 1.5%（简历数字的实验来源）；
  • 混沌注入：回传延迟放大 10 倍 → 超支率仍 < 3%（L3 硬上限兜住，验证防线独立性）；
  • pacing：消耗曲线贴目标轨迹线（格子口径偏差 < 10%），无尾部脉冲（最后 30 分钟消耗占比不高于全天均匀值 + 容差）；
  • L1/L2 一致性：日终 reserved 归零（所有预扣都被冲销或超时清算——超时清算任务：预扣后 N 分钟无回传视为流拍，自动冲销，防止 reserved 越积越多把预算卡死）。

03任务3 · 跨天预算重置与日切边界

问题驱动零点会发生什么

预算和频控一样是「自然日」口径（M2 已论证，对齐投放行业口径）。自然日意味着每天零点全部计划预算重置——两个坑：

  • 重置风暴：零点整批重建预算 key / 重置内存状态，瞬时写压力集中；
  • 日切归属：23:59:59.900 发出的决策，00:00:01 点击回传才到——这笔钱算哪天的？窗口在飞的请求横跨两天，账本归属不清则对账（任务 4）从第一天起就是糊涂账。

决策：三条规则

规则一：归属日 = 决策时刻

钱的承诺发生在决策时（L1 预扣时刻），所以预算归属日以决策时刻为准。回传无论多晚到达，凭 requestId 反查决策时间戳，入账到决策当天的账本。这条规则让跨天在飞流量有了确定归属：23:59:59.900 的决策算昨天的账，哪怕回传零点后才到。归属规则先于实现——没有这条规则，任务 4 的对账差异第一桶（时间窗差异）就无法自动归类。

规则二：新一天新 key，不用零点重置

预算状态键带日期：budget:campaign:{campaignId}:{yyyyMMdd}。新一天自然创建新 key，旧 key 当天不再被决策路径读写、留给对账读取后 TTL 过期。用命名空间消灭「零点全量重置」——没有重置操作，就没有重置风暴。这与 M1 缓存 TTL 随机偏移防雪崩是同一哲学：让时间自然分散危险操作。

规则三：时钟源统一 Redis TIME

「现在是哪一天」「现在是哪个 pacing 格子」这类判定必须用统一时钟。M2 频控已定 Redis TIME（Lua 内取时），预算沿用同一时钟源——频控的「今天」和预算的「今天」必须是同一个今天，否则会出现频控认为已重置而预算认为还没跨天的荒谬组合。多实例本地时钟漂移是分布式日切的经典事故源。

执行：日切时序推演

23:59:59.900  决策 D 发出，L1 预扣入 budget:c1:20261019（归属 19 日）
00:00:00.000  新 key budget:c1:20261020 就绪，新决策全部入新账
00:00:01.200  D 的点击回传到达（CPC 计费点）

              D 已实扣 → 无事发生；若 D 一直没回传 → 冲销预扣（流拍）

验收预期

  • 日切压测：零点前后 30 秒持续打流量，无重置风暴、无请求失败；19/20 两日账本之和 = 全部回传金额（归属无泄漏）；
  • 跨天在飞流量：日切窗口内决策 100% 正确归属（模拟器断言：账单金额按决策时间戳聚合后与两日账本精确相等）；
  • 连续 3 天跨零点运行：pacing 曲线每日零点平滑衔接，无跳变。

04任务4 · T+1 对账：证明系统没有撒谎

问题驱动没有审计的钱系统是黑箱

M0 的模拟器三合一设计中，媒体模拟器既负责回传（实时）又负责生成账单（T+1）——并且会故意制造两者不一致：按小概率丢回传、延迟回传、重复回传。这是模拟器的第四个隐藏角色：审计考官。如果 AdKernel 只记自己的账、从不与媒体账单比对，那么任务 2 的超支率、任务 3 的日切归属，全都建立在「系统自己说花了多少就花多少」的基础上。对账是数据闭环的最后一位审计员：用媒体的独立口径，验证我方账本的每一个数字。

决策：对账流水线

T+1 02:00 对账作业启动（避开零点窗口 + 跨天在飞已收敛）
  1. 拉取媒体账单（模拟器生成的 T 日账单文件，按计划聚合）
  2. 汇总我方账本 BudgetLedger（budget:c1:20261019 终态，同口径聚合）
  3. 双向差集：
     媒体有我无 → 丢单类      requestId 反查决策/曝光/回传三记录
     我有媒体无 → 误记类      本方记账 bug 或流拍误实扣
     双方都有金额不等 → 金额差异类
     双方都有 requestId 相同但多条 → 重复计费类
  4. 差异归桶（四桶模型）→ 前三桶自动处置，第四桶人工
  5. 输出对账报告 → 差异清零判定 + 告警

差异四桶模型（对账的差异定位方法论）

桶特征定位钥匙处置
① 时间窗差异回传跨天/延迟到达，两边归属日不同决策时间戳 vs 回传时间戳按归属日规则重算后自动消除（任务 3 规则一的直接受益者）
② 丢回传媒体账单有、我方账本无（点击发生了回传丢了）requestId 在我方决策记录中存在、回传记录中缺失按账单金额补记 + 标记补偿来源（M4 回传可靠性治理的入口伏笔）
③ 重复计费同一 requestId 多次回传requestId 幂等（M0 的贯穿钥匙第三次发力：频控、预算、对账三用）去重后自动消除；幂等没做好此桶会溢出
④ 真实 bug前三桶都归不进去逐条 requestId 完整链路回放唯一需要人工修复的桶：修代码 + 复盘 + 回归用例
四桶模型的价值：差异出现时第一反应不是「查日志」，而是「进哪个桶」——前三桶是系统的正常呼吸（时序固有属性），自动归类自动处置；只有第四桶值得人半夜爬起来。「T+1 对账清零」的严格定义：连续 7 天，①③桶自动归类率 100%、②桶补偿率 100%、④桶零新增。这是简历数字的验收口径。

05任务5 · 降级总开关：一键断电的分级设计

问题驱动组件级降级之上的系统级开关

M2 已经做了组件级分层降级（特征层保守 / 策略层中性 / 预算层拒绝），但组件级降级有一个盲区：它假设「问题出在某个组件」。三种场景组件级降级无解：

  • Redis 整体挂掉——M1 降级链走到 L2 就断了头（降级链自己的地基塌了）；
  • 发现策略 bug 正在大量错出价——需要立刻停用策略引擎，但 M2 的热更新需要先定位、再编译、再灰度，太慢；
  • 流量异常暴涨 10 倍且持续——限流在挡，但持续处于极限运行状态，应该主动收缩业务面。

需要的是一个站在所有组件之上的、不依赖任何被降级组件的、秒级生效的系统级开关。

决策：四级开关（不是单一 on/off）

级别名称行为业务代价
L0全开正常全链路—
L1人群包模式跳过策略引擎/频控/预算精细化，回退 M0 的预计算人群包直接决策精细度退化为 T+1 人群包水平（业务叙事闭环：RTA 降级为它要取代的东西，依然正确只是不聪明）
L2熔断缓存只读 L1 本地缓存画像、禁一切 Redis 访问（L2/频控/预算 Redis 侧全部冻结，预算走内存账本上限控制）频控失效风险 + 预算精度下降，由 L3 硬上限兜底
L3总停全部请求返回 noBid(reason=KILL_SWITCH)不参竞 = 不花钱 = 零损失，只是不赚钱
分级开关的设计哲学：降级的每一步都向业务方退让一个「更笨但更稳」的版本，而不是直接断电。L1 人群包模式是本设计的灵魂——它证明降级设计尊重业务语义：即使在最坏情况下，广告主的钱依然只花在目标人群上（M0 人群包本来就是「保底正确」的逻辑），损失的只是 M2 的精细化收益。面试讲到这里，降级从「技术兜底」升维成「业务连续性设计」。

执行：三条实现纪律

1. 开关状态本身用不可变 + 原子引用（M2 同款）

/**
 * KillSwitch：分级状态一次整体发布，读侧永远无锁。
 * 与 StrategyBundle 同一设计家族 —— 用不可变性消灭并发问题。
 */
record SwitchState(int level, String operator, String reason, Instant switchedAt) { }

static final AtomicReference<SwitchState> CURRENT =
    new AtomicReference<>(new SwitchState(0, "system", "init", Instant.MIN));

static void switchTo(int level, String operator, String reason) {
    CURRENT.set(new SwitchState(level, operator, reason, Instant.now()));
    auditLog.write(level, operator, reason);   // 纪律2：审计
}

2. 开关审计日志：who / when / why / 何时恢复

事故复盘的第一问永远是「谁在什么时候为什么关的」。每次切换写审计事件（进 M5 监控面板），审计通道本地文件直写，不经过任何可能正在被降级的组件。

3. 恢复必须人工确认，禁止自动回 L0

故障常呈抖动形态（好 30 秒坏 30 秒），自动恢复会导致开关震荡（降级-恢复-再降级），每次震荡都是一次流量损失。降级自动、恢复人工——宁可多降级一会，不可反复横跳。

致命坑预警：开关的配置通道绝不能依赖它要降级的组件。开关配置若存 Redis，Redis 挂掉时你正好需要打开 L2 熔断——而开关本身读不出来了。开关通道：本地配置文件 + 内存 AtomicReference 双通道，配置中心作为第三通道仅作常态分发。断电开关的电源线不能接在被断电的电路里。

验收预期（混沌演练 cell）

  • cell-1：注入 Redis 宕机 → 自动降至 L2 + 预算内存兜底生效，决策持续（命中 L1 缓存的请求正常出价，未命中按特征层降级语义拒绝），恢复人工确认后回 L0；
  • cell-2：注入策略 bug（错误 bidRatio）→ 人工 L1 人群包模式，60 秒内止血（全链路 noBid 化前完成切换）；
  • cell-3：流量 10 倍持续 5 分钟 → 限流 + L3 总停组合验证，系统存活、恢复后无损；
  • cell-4：开关震荡注入（模拟抖动故障）→ 验证「降级自动、恢复人工」纪律生效，无震荡。

06三张速览卡

卡1 · 限流选型速查
  • 口诀：保护自己用令牌桶，保护下游用漏桶
  • 三参数：rate 定长期均值、capacity 定可控突发（按下游瞬时承载反推，1-2 倍 rate）、拒绝策略（noBid 而非 429）
  • 三件套：降级联动 / 动态配置 / 监控告警——缺一件就是没测试过的保险丝
  • 三算法缺陷：固定窗口临界 2 倍突刺、滑动窗口内存高、漏桶拒绝一切突发
  • 实现纪律：惰性推算不用定时器、冷启动要预热、分布式要 Lua 原子
卡2 · 预算三级防线 + pacing
  • 本质难题：决策在先扣费在后 → 超花窗口只能对冲不能消灭
  • L1 预扣：决策时 estCost = bid × winRate × ctr（CPC 口径），乐观估计快速挡流量
  • L2 实扣：回传凭 requestId 冲销预扣 + 入真实金额，Lua 原子
  • L3 拒绝：剩余 < 5% 安全垫 → noBid，位置在策略引擎之前
  • pacing：5 分钟格子预算 + 目标轨迹线，追赶封顶防尾部 spike
  • 红线：硬上限 1.1× 日预算，80% 告警（Xandr 实证裁剪）
  • 超支 1.5% 构成：在飞窗口花费 + L1 估计误差
卡3 · 对账四桶 + 日切三规则
  • 日切规则：归属日=决策时刻 / 新日新 key 不重置 / 时钟源 Redis TIME
  • 桶①时间窗：跨天归属差异，规则一自动消除
  • 桶②丢回传：媒体有我无，requestId 定位，补偿入账打标记
  • 桶③重复计费：requestId 幂等去重
  • 桶④真 bug：唯一需要人工的桶，非零即告警
  • 清零口径：连续 7 天，①③自动归类 100%、②补偿 100%、④零新增

07动态雷达（2026 实证调研）

限流算法工程实践：令牌桶、漏桶与分布式限流（腾讯云开发者社区，2026-10）

「限自己的系统用令牌桶，限别人的系统用漏桶」选型口诀；分布式三方案（中心化计数 / 配额分片 / 云网关）；限流三件套（降级联动、动态配置、监控告警）。

单机限流多实例失效的完整论证；令牌桶 Lua 脚本（HMGET 存桶状态 + 时间差补令牌 + PEXPIRE 防冷 key 常驻）；多维度限流 key 设计。

采纳：任务 1 的 Lua 令牌桶实现范本；「读-判-写三步必须原子」与 M2 频控论据互相印证。

告别高并发接口被打爆：计数器、滑动窗口与令牌桶限流的落地实践（阿里云开发者社区，2026-09）

五个真实踩坑案例：固定窗口 2 倍突刺、capacity 过大等于没限、GET+DECR 竞态、多实例本地限流 N 倍放大、被限流返回 500 引发重试风暴。

采纳：五坑全部进任务 1 坑速查表——每个坑都有真实故障叙事支撑。

Daily Pacing（Microsoft Xandr 官方文档）

工业级 pacing lever 设计：约 15 分钟周期调节参竞速率；明确警告 spend spike 尾部风险（最后 30 分钟追赶爆冲）；daypart 限制下的分钟数口径。

采纳：15 分钟调节周期与 spend spike 警告进任务 2；「追赶封顶」规则的权威出处。

Key Budgeting and Pacing Concepts（Microsoft Xandr 官方文档）

Safety budget：硬性日消耗上限，建议 5-10 倍预期日消耗 + 80% 处自动告警；「无论 campaign 怎么配置，这个数绝对花不过」的兜底语义。

采纳：80% 告警点直接沿用；5-10 倍按自身架构裁剪为 1.1 倍（单时区单实例回传可控），「参数裁剪要有理由」的叙事素材。

Budget Pacing（OpenAI Ads 官方帮助中心，2026 更新）

pacing 的业务语义官方表述：「花费领先于节奏时放缓投放，落后时继续投放以追赶」；pacing 不保证均匀花费、不保证花完——管理预期而非承诺。

采纳：pacing 的业务定位表述进任务 2 开头（「花在什么时刻是效率的差别」）。
