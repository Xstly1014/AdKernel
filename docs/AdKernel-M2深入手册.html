AdKernel · M2 深入手册

策略是业务的大脑：改策略不停服（热更新）、策略坏了不拖垮主链路（安全降级）、新策略先灰度再全量（5% 试水）、多计划互不串扰（隔离路由）、同一个用户不被骚扰 N 次（频控）。M2 结束时：5+ 条广告人话策略在 Aviator DSL 上运行，压测中切换策略 QPS 零抖动，注入策略异常决策成功率不降，双计划消耗各归各账。

00M2 的定位与伏笔

为什么策略引擎排在缓存之后问题驱动

M1 锁定了特征契约（6 字段 × 消费方），M2 的第一条工作就是把"消费方"做出来——每条策略消费哪些特征字段，M1 的映射表已经写好，策略引擎是照着特征契约的图纸盖的房子。反过来做（先写策略再补特征）会造出悬空字段。另一个前置理由：策略求值必须快（延迟预算 15ms 里它占一块），而这依赖 M1 已经把特征查询的 P99 压到 2ms——大脑再聪明，供血不行也是白搭。

本册埋的伏笔

M2 埋的线在哪收
reason 决策原因码随响应返回M4 归因细分（按拒绝原因分布优化策略）；M0 裁判的断言依据升级
灰度 = userId 哈希取模 5%M4 AB 平台的雏形——M2 的简单哈希是 M4 一致性哈希分流的退化版，演进路径成面试叙事
策略 DSL 的规则文件外部化M4 对照实验：实验组/基线组策略 = 同一 DSL 引擎加载不同规则集——一次实现两处受益
频控检查串行在决策链上M5 调优战报现成素材：特征/频控/预算三 IO 并行化（CompletableFuture），P99 收益可量化
策略版本审计（变更留痕）M5 README 的"生产工程素养"证据；面试答"策略出问题怎么回滚"

01任务1 · 多计划路由

要解决的问题问题驱动

真实 RTA 服务同时跑多个广告计划（拉新计划 + 促活计划），各自独立预算、独立策略、独立人群。M0 的层级裁剪已定：计划 = 预算/策略/人群的独立控制单元（业界实证口径："预算只能按计划分配"）。本任务把这个"单元"落成代码结构——隔离不是把字段分开，而是把整条决策上下文分开：A 计划的策略崩了，不能影响 B 计划的决策。

决策：路由结构

// 计划注册表: 读写分离 —— 读热路径无锁(ConcurrentHashMap), 写只有配置变更
private final ConcurrentHashMap<String, CampaignContext> campaigns;

// CampaignContext: 一个计划的全部私有状态, 互相零共享
record CampaignContext(
  CampaignConfig config,                 // 日预算/人群包/出价上限/频控参数
  AtomicReference<StrategyBundle> strategies, // M2 核心见任务4: 独立热更新
  BudgetLedger budgetLedger             // M3 的预算账本: 每计划独立预扣/熔断
) { }

// 路由 = 一次 map 查找 + null 检查; 未知 campaignId → 快速失败(专用错误码)
// 丢弃方案: 单例 StrategyEngine + planId 参数贯穿 —— 字段隔离, 状态共享,
//          一个计划的策略对象崩了影响全局; 且热更新粒度被迫变成"全或无"
隔离的三层含义
① 数据隔离：预算账本每计划独立（M3 防超花按计划维度熔断）；② 故障隔离：策略求值异常只波及本计划（配合任务5 的默认策略，B 计划无感）；③ 更新隔离：A 计划灰度新策略时 B 计划的流量完全不动。三层隔离在面试里一层一层讲，比"我用了 Map"高一个维度。

验收预期

通过标准
  • 双计划并行压测（3 万 QPS 混合流量）：各自消耗/决策数/拒绝原因分布独立统计，交叉核对零串扰
  • 故障隔离实证：对 A 计划注入策略异常，B 计划决策成功率 100% 不受影响
  • 未知 campaignId 请求 → 专用错误码（不是 500 也不是 NPE），裁判（M0 模拟器）断言通过

坑速查表

症状原因处置
A 计划消耗莫名多扣两个计划共用了 BudgetLedger 实例（路由时浅拷贝）CampaignContext 构造器内 new 出全部私有状态；单测加"双计划预算独立"断言
新增计划要重启服务注册表没有管理接口留一个内部管理端点注册/注销计划（仅绑定 localhost）——顺带是 M5 可观测的挂载点

02任务2 · 规则 DSL：表达式层选型 Aviator

要解决的问题问题驱动

策略的业务本质是"条件 → 动作"：条件由特征字段构成（M1 的 6 字段），动作是拒/放/调系数。硬编码 if-else 的问题不是性能，是变更成本：投放策略一天一变，每次变更走发版 = 业务方说"改个判断条件怎么要排到下个版本"。规则引擎让"规则从代码剥离成配置，随时改随时生效"（2026 实证原话）。但选型前必须先回答：我们缺的到底是哪一层能力？

决策矩阵：四层定位，选表达式层

层代表解决什么AdKernel 需要吗
流程层LiteFlow组件串/并行编排（THEN/WHEN/SWITCH）× 决策链只有固定五级流水线，顺序从不变——编排引擎屠龙刀
规则层Easy-Rules / Drools规则集匹配、优先级、Rete 推理× 规则总量 5-10 条、无事实推理需求——Rete 是过度设计
表达式层（采用）Aviator条件表达式高性能求值✓ 策略条件全是单表达式；编译一次百万次求值毫秒级；白名单安全
语言层Groovy任意逻辑、完整编程× 可执行任意代码 = 安全审计不过；DSL 求值不需要一门语言
选型叙事的面试版本
"2026 年的规则引擎对比文章有个共识：LiteFlow 是施工总包、Easy-Rules 是施工规范手册、Aviator 是计算器、Groovy 是万能施工队——它们不在一个维度上，拿性能互比是关公战秦琼。我缺的只是表达式层：策略是 5-10 条'条件-动作'，五级流水线是固定骨架不需要编排，规则量级不需要 Rete。所以选 Aviator：编译一次后求值开销极小、默认白名单函数集（防注入）、语法类 Java 投放同学可读。"裁剪依据是需求分层分析，不是"哪个火用哪个"——这句话是整个选型决策的价值所在。

策略集：广告人话 → DSL（验收要件：每条必须业务语义可读）

// rules/campaign-001.properties —— 每条: 条件(Aviator) → 动作(target/bidRatio/reason)
// R1 已购保护: 已购未满7天 → 拒(钱不花在刚转化的人身上)
cond:  now - profile.lastConvertTime < 7*86400000
act :  {target: false, reason: "recently_converted"}

// R2 黑名单: 直接拒(风控名单)
cond:  profile.blacklisted == true
act :  {target: false, reason: "blacklisted"}

// R3 高价值沉默: VIP + 沉默(30天未转化) → 加价 1.5 倍触达
cond:  profile.memberLevel == 'VIP' && now - profile.lastConvertTime > 30*86400000
act :  {target: true, bidRatio: 1.5, reason: "high_value_silent"}

// R4 新用户保守: 首次出现<3天 → 中性参与(无历史数据不加价不减价)
cond:  now - profile.firstSeenTime < 3*86400000
act :  {target: true, bidRatio: 1.0, reason: "cold_start_neutral"}

// R5 低价值压价: 普通会员且7-30天内转化过 → 降价 0.5(已过 R1 的 7 天保护期, 但仍有近期转化, 触达价值低)
cond:  profile.memberLevel == 'NORMAL' && now - profile.lastConvertTime < 30*86400000
act :  {target: true, bidRatio: 0.5, reason: "recently_converted_lowvalue"}

// 规则求值: 短路有序(R1→R5), 首个命中即返回; 全不命中 → 默认动作(见任务5)

注意规则间的顺序即优先级（R1 已购保护排在 R3 高价值前——VIP 用户刚转化也要拒）：优先级语义显式写在规则文件头部注释，这是投放同学的"操作手册"而不是程序员的代码。

执行细节：预编译缓存

Aviator 的生产实践（2026-10 实证）：表达式字符串 → compile() 一次 → Expression 对象反复 execute(env)。编译开销发生在策略加载时（冷），求值走预编译对象（热路径零编译）。坑：表达式缓存以字符串为 key，规则文件里多一个空格就是新 key——缓存键做规范化（去空白）后再作 key，防缓存泄漏（实证坑点）。

验收预期

通过标准
  • 5+ 条策略全 DSL 化运行，每条带 reason 码；裁判断言：黑名单用户必拒（R2 生效）
  • 策略求值延迟：单条表达式求值 P99 < 0.1ms（预编译后），策略链整体 < 1ms
  • 规则优先级语义验证：VIP 已购用户命中 R1 而非 R3（构造用例断言）

坑速查表

症状原因处置
压测中出现偶发 NPE 中断决策表达式里 profile.lastConvertTime 为 null（新用户无转化记录）Aviator 空值陷阱（实证坑）：env 填充前统一补默认值（lastConvertTime 缺省 = epoch）；或 DSL 用 include 判空——规则生成器统一处理，不靠规则编写者自觉
改了规则文件重启才生效忘了接 watch 机制（任务4 的热更新是 DSL 价值的一半）任务4 一起验收——"热更新不了"的 DSL 等于没做
规则越加越多后可读性崩坏规则间隐式依赖（R3 依赖 R1 先拒）顺序即优先级必须成文；>15 条时才考虑升级规则层引擎（Easy-Rules），当前量级不预优化

03任务3 · 频控

要解决的问题问题驱动

频控的业务动机：同一个用户一天被同一计划曝光 10 次，第 11 次不但无效（用户已无视），还伤害品牌——频控是用户体验和预算效率的双重约束（M0 名词表口径）。工程动机：频控计数是决策链上的第二个外部 IO（第一个是特征），它的窗口算法与原子性直接决定正确性和延迟。

决策一：为什么频控在策略层而不是接入层

面试深挖题 11 的答案在此：接入层做通用防护（限流/鉴权/协议），策略层做业务规则——频控上限是每计划各不相同的业务参数（拉新计划严、品牌计划宽），它消费 M1 的特征（impressionCount7d）与决策上下文（campaignId），语义上属于"这个计划要不要参竞"判断的一部分。放接入层会让接入层依赖业务配置，分层崩坏。

决策二：窗口算法——自然日计数 + 明确局限

方案语义坑判定
自然日 INCR（采用）"每日不超过 N 次"——对齐投放行业的频控口径（投放后台配的就是日频控）窗口边界双倍脉冲（23:59:59 曝光 N + 00:00:01 又 N）✓ 频控防的是"骚扰"，不是黑产攻击——边界处多曝光几次用户体验影响有限；脉冲局限写进 ADR
ZSet 滑动窗口近 24h 连续窗口，零脉冲每用户每计划一个 ZSet，内存 O(曝光数)；黑产对抗场景才必要× 防刷单口径的方案（2026-10 实证是黑产场景）；升级路径在 ADR 注明

决策三：计数时点——检查在决策，记录在回传

// 频控的时序困境: 决策时(参竞瞬间)该曝光还没发生, 竞价还可能输
// → 检查(决策链): GET freq:{campaignId}:{userId} → ≥N 则 reason=freq_capped 拒
//   记录(回传处理): 收到 EXPOSURE 回传事件时 INCR
// 语义: 本次决策用"截至上一次曝光"的计数 —— 滞后一拍是语义妥协:
//   媒体回传本身有秒级时延, 频控本来就是近似的(业界同款);
//   换来的是"不预扣不透支" —— 参竞≠曝光, 竞价输了不该计数
//
// 原子性: 检查在决策链(读), 记录在回传流(写), 读写异流无竞态;
// INCR+EXPIRE 用 Lua 一次往返(INCR / 到次日零点 EXPIRE / 判定 三步原子)
// 时钟: 用 Redis TIME 而非应用时钟 —— 计算次日零点口径, 消除多实例时钟漂移
Lua 原子性的选型论据（顺带覆盖 M3 限流的知识点）
Redis 原子执行有三条路：MULTI/EXEC 不能在事务内读值后分支（频控需要"读了计数再决定写不写"）；WATCH+MULTI 高并发下冲突重试风暴（"争抢越激烈重试越多"——最坏行为）；Lua 脚本 原子执行、可 if/then 分支、单次往返（TOCTOU 竞态的标准解）。频控/限流这类"读-判-写"三步操作，Lua 是唯一正解——这条论据 M3 限流直接复用。

验收预期

通过标准
  • 频控生效实证：单用户定向流量打满 N 次/日后，裁判断言后续参竞决策全部 reason=freq_capped
  • 滞后一拍语义验证：第 N+1 次决策在回传未到达前仍放行（设计如此），回传落地后拒绝——行为与文档口径一致
  • 跨零点测试：日切时计数归零、EXPIRE 不留死 key

坑速查表

症状原因处置
频控 key 堆积内存EXPIRE 忘设或设成了"无当日语义"的固定值EXPIRE 到当日 24 点（Redis TIME 计算）；冷用户 key 次日自动蒸发
频控查询拖慢决策链频控 GET 与特征查询串行执行当前先记录数字（M5 伏笔：三 IO 并行化）；单次 GET ~1ms 在预算内
计数永远比实际曝光少只统计了 AdKernel 参竞的曝光，但频控语义含媒体全量曝光（跨计划）简化口径成文：AdKernel 频控只约束本系统参竞带来的曝光；真实系统媒体侧有全量频控，ADR 写明边界

04任务4 · 热更新与灰度

要解决的问题问题驱动

DSL 的价值一半在"规则是配置"，另一半在"配置改了立即生效"——没有热更新的 DSL 只是搬了家的 if-else。同时，直接全量上新策略 = 拿全量预算赌新策略：新规则有 bug 时 3 万 QPS 全部错误决策。所以热更新必须自带灰度：新策略先放 5% 流量，观察无异常再全量。

热更新：AtomicReference 原子切换

// StrategyBundle: 一组预编译好的规则(不可变对象), 整体替换而非逐条改
public final class StrategyBundle {
  final List<CompiledRule> rules;  // 顺序即优先级, 编译期固定
  final String version;           // 版本审计: 谁在何时把 v3 换成 v4
}
// 切换: strategies.set(newBundle) —— 引用替换, 读侧永远拿到完整一致的 bundle
//   正在求值旧 bundle 的请求自然跑完(旧对象不可变, 不会被改坏)
// 写侧: watch 线程发现规则文件变更 → 编译新 bundle → 编译失败=拒绝切换(旧版本继续服务)
//       → set() 替换 → 记录审计日志(version/operator/规则摘要)
// 读侧: 决策链每次请求 get() 一次 —— 无锁, 无拷贝
为什么 AtomicReference 就够（而不是读写锁）
ADX 实证模式同款。核心洞察：策略集是不可变对象 + 引用替换——读者拿到旧引用就安全跑完旧逻辑，新读者拿到新引用跑新逻辑，中间不存在"改了一半"的状态。读写锁解决的是"可变对象的部分更新"问题，而我们根本不做部分更新。这就是"用不可变性消灭并发问题"——面试讲并发时的高分素材。

灰度：userId 哈希取模 5%（M4 AB 平台的雏形）

// 新版本 bundle 上线: hash(userId) % 100 < 5 → newBundle, 其余 → oldBundle
//   哈希而非常量开关: 同一用户稳定落在同一侧(不会今天新策略明天旧策略)
//   —— 这就是 M4 一致性哈希分流的退化版, 届时演进为正式实验平台
// 回退: 灰度期间异常率/拒绝率异常 → set(oldBundle) 一键全量回退, 秒级
// 观察指标: 新策略组的决策率/bidRatio 分布/reason 分布 vs 旧策略组 —— M5 面板出对比曲线

验收预期

通过标准
  • 压测中改规则文件（bidRatio 1.5→2.0）：新决策即时生效（下一个请求起），QPS/延迟曲线零抖动
  • 编译失败保护：写入一条语法错误的规则 → 切换被拒、旧版本继续服务、告警埋点触发
  • 灰度生效：5% 流量 reason/决策分布与 95% 显著不同；一键回退 < 1s 生效
  • 版本审计：每次切换留痕（版本号/时间/规则摘要），可查最近 10 次变更

坑速查表

症状原因处置
热更新后偶发 ClassCastException规则里引用的自定义函数类被重新加载（类加载器泄漏）Aviator 自定义函数用静态注册（全局一份），规则文件只存表达式不存函数定义——函数属于代码不属于配置
灰度组流量比配 5% 偏差大userId 哈希分布不均（模拟器 ID 生成有模式）用 murmur3 等雪崩哈希；灰度比例断言 ±0.5% 内进冒烟
watch 误触发频繁重编译编辑器保存产生临时文件/多次写事件watch 去抖（500ms 静默期）+ 内容哈希比对（变了才编译）

05任务5 · 安全降级：策略异常不阻断主链路

要解决的问题问题驱动

策略是业务大脑，但大脑抽风不能心脏骤停：新上的规则有 bug（空指针/除零/类型错）、Aviator 求值抛异常时，决策不能失败——失败的代价是媒体按超时/错误处理，错误率超红线照样被清退（M0 的生存指标）。ADX 实证原话："策略异常不阻断主链路。"

分层降级语义（本任务的核心设计）

层降级触发降级动作为什么是这个语义
特征层（M1 已建）查不到数据（超时/miss）保守：默认画像→不参竞/低出价信息不足时宁可不做——没有数据支持的决策是赌博
策略层（本任务）有数据没逻辑（规则抛异常）中性：target=true + bidRatio=1.0（无策略基线）特征数据是可信的，只是策略坏了——回退到"无 RTA 增益"的基线投放，损失的只是优化增益，不损失基本投放
保守与中性的区别是本设计的心脏：特征层降保守（缺数据=拒绝），策略层降中性（缺逻辑=基线）——降级的默认值由"缺的是什么"决定，不是拍脑袋统一返回拒绝。面试被问"降级策略怎么设计"时，这个分层论证比"我们都返回默认值"高两个段位。每次策略降级：reason=strategy_fallback + 告警埋点（degraded_strategy 计数，M5 面板）。

验收预期

通过标准
  • 注入实验：压测中热更新一条会抛异常的规则 → 触发策略层降级 → 决策成功率 100%、P99 无尖刺、degraded_strategy 计数与异常规则命中数一致
  • 降级语义正确：降级响应 bidRatio=1.0/target=true，裁判按"中性参与"校验通过
  • 隔离联动：异常规则只影响其计划（A 计划降级中 B 计划策略正常，任务1 的故障隔离实证）

坑速查表

症状原因处置
降级后决策率暴跌默认值设成了 target=false（保守）而不是中性对照分层语义表：策略层=中性基线；决策率是媒体考核指标，全拒=自废武功
异常规则持续吃流量降级吞了异常但没人知道降级率进告警（M5）；灰度发布的意义就是让异常规则只碰 5% 流量
规则异常导致响应超时求值外层没 catch 或 catch 后做了重试策略求值一次、不重试、不重载——快失败快降级；重试留给写入侧（回传流）

06速览卡 · 规则引擎四层定位（面试高频）

层代表类比一句话
流程层LiteFlow施工总包管组件怎么跑（THEN/WHEN/SWITCH 编排），不管组件干什么
规则层Easy-Rules/Drools施工规范手册条件-动作规则集匹配与推理（Rete），适合规则多且需推理
表达式层Aviator/MVEL/SpEL计算器单表达式高性能求值，编译一次跑百万次
语言层Groovy万能施工队一门完整语言，自由度最大、安全风险最大（可执行任意代码）

AdKernel 选型答案："四者不在一个维度（拿它们比性能是关公战秦琼）。我缺的是表达式层：策略=5-10 条条件-动作，流水线骨架固定不需要编排，规则量级不需要 Rete。Aviator——编译求值快、白名单安全、语法投放同学可读。"先做需求分层，再选工具，这是方法论不是知识点。

07速览卡 · 频控设计（口袋版）

要点内容
业务动机用户体验 + 预算效率双约束（第 11 次曝光无效且伤品牌）
分层归属策略层（业务规则、每计划独立参数），不是接入层（通用防护）
窗口口径自然日计数（对齐投放行业"日频控"口径）；边界脉冲局限写 ADR，升级路径=ZSet 滑动窗口（防黑产场景才必要）
计数时点检查在决策（GET）、记录在回传（INCR）——参竞≠曝光，竞价输了不计数；滞后一拍是语义妥协（业界同款）
原子性INCR/判定/EXPIRE 用 Lua 单次往返——TOCTOU 标准解；MULTI 不能分支、WATCH 高并发重试风暴
时钟Redis TIME 取时（算次日零点 EXPIRE），消除多实例时钟漂移

08速览卡 · 分层降级语义（面试两段位素材）

降级层缺什么默认值语义
特征层缺数据保守（不参竞/低出价）信息不足宁可不做
策略层缺逻辑中性（基线参与 bidRatio=1.0）数据可信，回退无增益基线
预算层（M3）缺额度拒绝（reason=budget_exhausted）钱花完了就是花完了

核心句："降级的默认值由缺的是什么决定——缺数据保守、缺逻辑中性、缺额度拒绝。统一返回一个默认值是把三个不同的失败当成一个处理。"

09动态雷达 · 2026（M2 相关）

2026-09-15方法论：Java 规则引擎选型对决（LiteFlow/Easy-Rules/Aviator/Groovy）——四者定位分层（编排/规则/表达式/语言），"规则引擎不是银弹，选对了才是解药"；选型先问业务在哪一层需要规则能力。对项目的影响：任务2 决策矩阵的四层框架直接来源；"关公战秦琼"的选型叙事出处。
2026-10-13实证：Aviator 从选型到生产级规则引擎落地——四维评估（语法/性能/安全/生态）；生产架构三件套：缓存预编译 + 灰度发布 + 版本审计；生产坑：空指针陷阱、表达式缓存泄漏、类加载冲突。对项目的影响：任务4 热更新+灰度+审计的架构直接对齐该实证；空值陷阱与缓存键规范化坑的出处。
2026-09-23架构：决策系统四层拆分（流程/规则/表达式/语言）——"明明只需要表达式计算能力，非要引入完整规则引擎，维护成本比业务代码还高"；Groovy 脚本当瑞士军刀 → ClassLoader 内存告警。对项目的影响：裁剪论据（不引 LiteFlow/Easy-Rules）的引用出处；防过度设计的正面案例。
2026-03-20官方：Redis 五种限流算法对比（Redis 官方教程）——fixed window（边界 2x 突发）/sliding window log（ZSet 精确）/token bucket（允许突发）/leaky bucket（严格平滑）对比表；原子性三方案（MULTI 不能分支、WATCH 重试风暴、Lua 单次往返可分支）。对项目的影响：频控窗口算法决策依据；Lua 原子性论据（M3 限流复用）。
2026-10-15实战：Redis ZSet 滑动窗口限流防黑产刷单——"窗口临界点双倍脉冲"：黑产在 00:00:00.999 与 00:00:01.001 各打 100 次，2ms 内 200 并发突破 100 QPS 底线；ZSet 四步（清理/统计/判定/过期）+ 原子 Lua。对项目的影响：自然日窗口的脉冲局限论证来源（频控防骚扰 vs 防黑产的口径区分）；升级路径的参照实现。
2026实证：在线策略引擎设计（ADX 案例，v1 调研延续）——策略模式+模板方法框架、AtomicReference 本地缓存热更新、"策略异常不阻断主链路"、本地限流器、"离线负责算在线负责判"。对项目的影响：任务4/任务5 的核心模式出处（AtomicReference 不可变替换、异常不阻断）。
