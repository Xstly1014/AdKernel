M4 · 归因回流、特征近线更新与 AB 实验

AdKernel 里程碑四 —— 让系统「会呼吸」：转化回流改写画像，画像影响下次决策，AB 实验证明这一切真的有效。

00总纲与伏笔收线

M3 结束时，AdKernel 已经是一个「花钱有纪律」的系统：限流挡住自己打挂自己、预算三级防线防超花、对账证明每一分钱的清白、总开关保底生存。但到现在为止，这个系统还只能算「单向流水线」——画像数据是投放前预置好的静态货物（M0 的内存 Map），策略再聪明，学的也是昨天的世界。M4 是整个项目的灵魂里程碑（Spec v2 降级线定义）：补上归因 → 回流 → 近线更新 → 影响下次决策的数据飞轮，并用 AB 对照实验把「飞轮真的在转」这件事变成统计上站得住脚的数字。

M4 与简历数字的对应关系（resume0.2.tex 第三、四条 bullet 溯源）：第三条「转化回流数据闭环：已转化即排除端到端 < 5s」= 任务 2 端到端验收；第四条「AB 实验体系：CPA 优化 12%」= 任务 5 对照实验结论。两个数字都在本册闭环，简历第三、四条 bullet 从此全部两跳可溯源（L1 85%、12ms→2ms 等性能数字按 Spec v2 定版原则不上简历，是 M1 交付的追问弹药）。

01任务1 · 归因引擎：转化的功劳记给谁

问题驱动为什么必须先有归因

用户在 8:00 看到计划 A 的广告没买，10:00 看到计划 B 的广告买了——这单转化记给谁？没有归因引擎，M0 的转化回传只是一条孤立记录，回流（任务 2）无从谈起：不知道功劳属于哪次决策，就不知道该更新谁的画像、该把成本记在哪个计划头上、该让哪个策略变聪明。归因是回流的第一道工序，也是实验报表（任务 5）口径的地基——归因的分歧很少发生在算法上，多发在同一个词指的不是同一件事上（动态雷达实证），所以归因引擎的第一交付物不是代码，是口径。

决策：模型与口径三选

归因模型规则业界采用评价
末次点击（LCA）✓功劳记给转化前最后一次点击的广告Microsoft Advertising 默认、Apple AdAttributionKit、Google Ads 可选简单、可解释、行业标准默认
首次点击功劳记给第一次点击Adobe 报表可选项高估拉新渠道
数据驱动机器学习按历史转化学出各触点权重Google Ads 可选项准确但不可解释、冷启动无数据

选末次点击，理由要讲清楚（不是「因为简单」）：①行业默认口径（Microsoft/Apple 均默认 LCA），与媒体账单口径对齐——归因口径必须能和 M3 对账口径互相对上，自定义口径会让对账差异④桶常态化；②AdKernel 的业务初心是「已购保护 + 差异化出价」（M2 策略 R1），转化前最后一次触达是影响决策的最直接证据，末次点击与此业务语义天然一致；③可解释性是实验平台的硬需求——每个归因结果都能用人话讲给广告主听。末次点击不是错，它只是把功劳记给了最后一个到场的人；等数据量足够，数据驱动模型是演进方向（M5 之后的路线图话题）。

口径三要素（每项都要写成配置常量，单点定义）

  • 归因窗口：转化发生前多少天内的点击可参与归因。Microsoft 口径 1 分钟~90 天、默认 30 天。AdKernel 裁剪：7 天——电商拉新场景决策周期短，窗口越长稀释效应越强（30 天前的一次点击对今天下单的贡献近乎玄学）；窗口长短是「因果强度」与「归因覆盖率」的权衡，7 天是漏斗参数（funnel.yaml）的一部分，可随实验调整。
  • 计数口径：All（每次转化都计，适合购买）vs Unique（只计首次，适合线索）。AdKernel 选 All——已购保护策略（R1）需要知道用户的完整购买历史，重复购买正是画像特征 lastConvertTime 要更新的对象。
  • 无点击兜底：Last Touch 语义——窗口内无点击时记给最后一次曝光（Microsoft VTC 浏览归因语义）。AdKernel 暂不实现 VTC（模拟器不生成浏览型转化），但在归因引擎里留 ATTRIBUTION_MODE 枚举位——口径演进的接口先行，与 M3 RateLimitGate 同一手法。

执行：归因匹配流水线

转化事件到达（transUniqueId 携带 userId + 转化时间 + 转化类型）
  1. 查点击索引：click:{userId} → ZSet（score=点击时间, member=requestId）
     （M0 五类记录之「点击记录」——M2 频控同款 ZSet 结构，此处第三次复用）
  2. 取转化时间前 7 天内、最近一次点击的 requestId
     窗口内无点击 → 未归因事件（unattributed），单列监控——比例异常=回流断链信号
  3. 凭 requestId 反查决策记录 → 得到 campaignId / expId / 策略版本
     （M0 requestId 贯穿在此转动：转化→点击→决策 三级反查，全链路一条线）
  4. 写归因结果：attribution = {requestId, campaignId, expId, 转化金额, 归因模型, 归因耗时}
  5. 发布「已归因转化」事件 → 任务2 回流链路的入口
关键设计：归因日志是不可变事实（immutable fact）。归因结果只追加、不修改——对账（M3）与实验报表（任务 5）都以归因日志为唯一事实源。若归因口径日后调整（如窗口 7 天改 14 天），做法是重放归因（replay），生成新版本归因日志，而不是原地改写——历史报表永远可以复现，这是实验平台可信度的底线。

验收预期

  • 构造多计划多触点用户序列（A 点击→B 点击→转化）：100% 归因给 B（末次点击语义）；
  • 窗口边界：6.9 天前的点击归因、7.1 天前不归因，边界精确到秒；
  • 未归因比例：正常日 < 5%（模拟器漏斗参数控制），超阈值告警（回流断链预警）；
  • 归因引擎 P99 < 50ms（ZSet 单 key 读写，非决策路径，预算宽松但仍有上限）。

02任务2 · 转化回流链路：mini-MQ 上场，回流<5s

问题驱动回流为什么是一条独立链路

归因完成的转化事件需要送达两个下游：特征近线更新（任务 3）和实验指标聚合（任务 5）。三个不能用同步调用解决的理由：①转化到达有脉冲性（模拟器漏斗的 cvr 事件在头部用户上高度聚集），同步更新会打穿特征存储；②更新链路故障绝不能反噬决策主链路——回流挂了广告照样要投，只是暂时变笨；③实验指标聚合是天然的可异步累加计算。需要削峰、解耦、故障隔离——这个需求画像就是消息队列。而项目组合里恰好有一个 mini-MQ：造了轮子，还造了用轮子的车（Spec v2 的双项目闭环叙事在本任务落地）。

决策：回流链路拓扑

归因引擎 ──发布──▶ mini-MQ topic: conversion-attributed
                        │
        ┌───────────────┴───────────────┐
   consumer: feature-updater      consumer: metrics-aggregator
   （任务3 近线更新）               （任务5 实验指标累加）
   独立消费组、独立 lag 告警、独立降级开关（KillSwitch 扩展位）

两个消费组物理隔离（mini-MQ 的消费组语义），一方积压不拖另一方；metrics-aggregator 只做无状态累加，挂了可重放恢复（消费位点回退），feature-updater 有副作用需幂等（见坑表）。

回流 < 5s 的端到端分解（简历数字的账本）

环节预算说明
转化回传接收 → 归因完成< 100msZSet 反查 + 记录写入，内存操作
归因发布 → mini-MQ 可见< 1s组提交落盘 + 副本同步（mini-MQ M2 ISR 语义的延迟特性）
broker → consumer 拉取< 2s消费批量大小与拉取间隔的权衡，回流链路选小批量低延迟模式
consumer 处理 → 特征更新生效可见< 2s近线更新写源 + 缓存失效（任务 3 详述）
合计 P99< 5s各段 P99 相加偏保守，实测通常更优——简历口径取端到端 P99

执行：回流可靠性治理（M3 对账桶②「丢回传」的事前预防）

M3 的对账只能事后发现媒体且回传（账单有、我方无）并补偿。M4 在我方内部链路上把可靠性前移：

  • 发送侧：归因结果本地 WAL 短暂持久化后再确认发布（mini-MQ 生产者确认语义），发布失败重试三次后落补偿队列——归因日志是不可变事实（任务 1），WAL 与它同源；
  • 消费侧：幂等消费（transUniqueId 作为去重键——M0 协议字段第四次复用：频控、预算、对账、回流四用），重复投递不产生双重更新；
  • 终态对齐：每日对账作业（M3 流水线）新增一桶校验——归因日志条数 = MQ 已消费确认数 + 补偿队列数，回流链路自身的账也要对得上（审计员也要被审计）。

验收预期

  • 端到端回流 P99 < 5s（简历数字实验来源），P50 < 2s；
  • 注入 consumer 宕机 10 分钟：恢复后重放补齐，特征最终一致，无重复更新（幂等验证）；
  • 注入 MQ 不可用 30 分钟：决策主链路零影响（回流降级模式：转化暂存 WAL，恢复后追赶）；
  • 五段延迟打点全部上线——M5 可观测的伏笔。

03任务3 · 特征近线更新：让画像学会呼吸

问题驱动近线（near-line）是什么、为什么不是实时或离线

M1 的 UserProfile 是投放前预置的静态画像，M2 的策略依赖它做精细化判断——但 lastConvertTime（已购保护 R1 的依据）和 impressionCount7d（频控参数）这些字段的真实语义是随业务运行持续变化的状态。更新时机的三档选择：

档位延迟代价问题
实时（决策路径内同步更新）0决策路径加写放大污染 60ms 预算；画像系统故障直接打挂决策
离线（T+1 批处理）1 天最低就是 RTA 要取代的「人群包 T+1 痛点」——自废武功
近线（事件驱动的准实时）✓秒级中等存在短暂的状态滞后（可量化、可接受）

近线是 RTA 叙事的自我一致点：业务初心的起点就是「T+1 人群包太慢」，自己的特征更新绝不能再退回 T+1。秒级近线 = 比实时便宜、比离线新鲜，延迟由任务 2 的回流链路预算（<5s）统一背书。

决策：更新语义与失效策略

1. 幂等更新：绝对值覆盖，不做增量累加

// feature-updater 消费「已归因转化」事件后的更新动作
// 关键纪律：覆盖式更新（set），不是累加式（incr）—— MQ 重投不产生偏差
profile.setLastConvertTime(event.convertTime());     // R1 已购保护即刻生效
profile.setMemberLevel(recompute(event.userId()));   // 按业务规则重算等级
// impressionCount7d 的滚动窗口另由曝光计数任务维护（见下）

计数型特征（impressionCount7d）是仅有的增量语义特征，其幂等性由 requestId 维度去重计数保证（Redis HyperLogLog 或 Set 去重 + 计数），而非裸 INCR——与 M2 频控的「检查在决策、记录在回传」不同，此处计数的正确性优先于成本。

2. 缓存失效：让 M1 的三级缓存看见新画像

源更新后，L2（Redis 画像缓存）直接删除对应 key（删除而非更新——下次回源自然加载新值，用 M1 已有的回源机制做同步，不新造同步路径）；L1（Caffeine）不主动失效——沿用 M1 参数 refreshAfterWrite 15s 的既有语义：最多 15 秒后异步刷新拿到新值。近线更新的可见延迟 = 回流延迟（<5s）+ L1 刷新窗口（<15s），合计 P99 < 20s——对「7 天内已购保护」这种粒度的业务语义，20 秒的收敛时间完全无感，这个「不需要更快的理由」是面试的加分回答。

3. 更新风暴防御：头部用户的写入脉冲

幂律流量下转化同样幂律集中（M0 设计的既定事实），头部用户的特征更新是高频小事务。防御三层：①更新按 userId 哈希分片到多 updater 并行消费；②同用户短窗口内多条事件合并更新（500ms 微窗口聚合，重复覆盖天然无害——幂等语义的红利）；③特征源写入走异步批量缓冲，背压时丢弃的是更新时效而非更新正确性（下一次覆盖更新自愈）。

验收预期

  • 转化 → 策略生效端到端：P99 < 20s（回流 5s + L1 刷新 15s），模拟器断言「已购用户在转化后 20s 内的新决策 100% 被策略 R1 拒绝」；
  • MQ 重放 3 次同一事件：lastConvertTime 等覆盖型特征零变化，计数型特征零偏差（幂等验证）；
  • 特征源写入 P99 < 10ms，头部用户聚合后写入 QPS 可控（无脉冲穿透）。

04任务4 · AB 实验分桶：M2 灰度的升级与正名

问题驱动从「5% 灰度」到「实验平台」差的是什么

M2 的策略热更新带着 userId 哈希 5% 灰度——但灰度只回答「新版本安不安全」，不回答「新版本好不好」。差的正是分流基础设施的系统性设计：分桶必须无偏、可重复、可并行、可校验。四条硬要求推导出分桶平台：①同一用户永远进同一组（决策一致性，否则同一用户策略反复横跳）；②分桶结果只由 (userId, 实验) 决定，可离线复算（审计）；③多实验并行互不污染；④分完能证明「分得均匀」（不然一切对比都是自我安慰）。

决策一：一致性哈希分桶（MurmurHash + salt）

/**
 * 分桶：userId + salt(experimentId) → MurmurHash3 → [0, 1000) 桶号
 * - user_id 必须稳定（M0 协议 userId 即登录 ID，天然满足）
 * - experimentId 参与 salt：多实验间天然隔离，无偏可复算
 * - MurmurHash 而非 MD5：均匀性相当、开销低一个量级（动态雷达实证）
 */
static int bucket(String userId, String experimentId) {
    byte[] key = (experimentId + ":" + userId).getBytes(UTF_8);
    int hash = Hashing.murmur3_32_fixed().hashBytes(key).asInt();
    return (hash & Integer.MAX_VALUE) % 1000;   // 桶号 0~999
}
// exp001「RTA vs 人群包」: 桶 0-499 → 对照组, 500-999 → 实验组（各 50%）
// M2 的「哈希 5% 灰度」即本函数在桶区间 [0, 49] 上的特例——灰度是分桶的子集

决策二：互斥还是正交——广告实验的答案与通用结论相反

通用 AB 平台方法论是「正交分层」：不同实验作用于不同业务环节，各自成层、salt 隔离、同用户可多层并行（流量复用率高）。但广告场景有特殊性（动态雷达 CSDN 实证明确点名）：广告位/预算是稀缺竞争资源，作用于同一资源池的实验互为干扰——两个策略实验同时抢同一批曝光，指标差异反映的是「混战中抢到的量」而非策略本身的优劣。AdKernel 的裁剪：

实验域关系理由
exp001：RTA vs 人群包（同一计划的两种模式）互斥（用户分流）同一用户要么走 RTA 决策要么走人群包，绝无叠加——对照组的纯净性是实验成立的前提
exp002：计划级策略变体（未来：出价策略迭代）与 exp001 正交分层作用环节不同（exp001 是决策模式，exp002 是策略参数），层间 salt 隔离（exp001 / exp002 各为 salt），可并行

「互斥保证纯净、正交提升效率」——同一套分桶函数，两层实验域，这就是分层正交的最小完整实现；未来新实验按「是否作用于同一资源池」进互斥域或正交层。

决策三：分桶质量的自我证明（AA 校验 + SRM 检测）

  • AA 测试：正式实验前，两组跑完全相同的策略（A vs A），对比北极星指标——差异应不显著。不显著才能证明「分桶本身无偏」，实验的对照组才可信；
  • SRM 检测（Sample Ratio Mismatch）：运行期持续校验两组流量占比是否偏离设计比例（50/50），χ² 检验。SRM 触发 = 分流被什么东西污染了（如实验中途改配置、哈希输入不稳定），此时一切指标对比作废，先修分流再谈效果；
  • expId 全链路透传：分桶结果写入决策请求上下文（M2 预留的 expId 字段），决策/曝光/转化/归因全链路携带——报表按 expId 自动分组，无人工标记环节（消除「实验组数据缺失」这类经典事故）。

验收预期

  • 分桶均匀性：AA 测试 7 天，两组北极星指标差异不显著（p > 0.05）——分桶无偏的证据；
  • 一致性：同一 userId 十万次分桶结果 100% 相同；离线复算与线上分组零偏差；
  • SRM 陪跑：正常日 SRM 零告警；注入「中途改流量比例」故障，SRM 检测在 1 小时内报警；
  • M2 灰度迁移：策略热更新的 5% 灰度改走分桶平台（同一函数），行为零变化——基础设施统一完成。

坑速查表

坑症状药方

05任务5 · RTA vs 人群包对照实验：CPA 12% 的诞生

问题驱动项目的价值证明闭环到最后一环

Spec v2 的业务初心叙事表要求「有效性证明」：RTA 比人群包好在哪、好多少、你凭什么信？这是 M0 就立下的军令状，也是简历 bullet「CPA 12%」的实验来源。没有这个实验，AdKernel 讲得再好也只是「我实现了」而不是「它有效」——这是整个项目从工程叙事升维到业务叙事的验收节点。

决策：实验设计五要素

要素AdKernel 设计依据
假设RTA 毫秒级个性化决策降低已购误投、提升出价精准度 → CPA 下降M0 业务初心叙事链
分桶exp001 互斥分流 50/50，两组除决策模式外一切同构任务 4 分桶平台
北极星指标CPA = 计划消耗 / 归因转化数广告主的终极问题就是「一个转化多少钱」
护栏指标两组花费偏差 < 5%（M3 pacing 收线）、决策 P99 无劣化、SRM 不触发花费不公平的对比没有意义——成本侧公平性先行
诊断指标reason 码分布（R1 已购拒绝占比）、bidRatio 分布、未归因率解释「为什么实验组 CPA 更低」——M2 reason 码伏笔收线

对照组定义：人群包模式 = M3 KillSwitch L1 的正向复用

对照组跑的正是 M3 降级总开关的 L1 模式（预计算人群包直接决策）——降级模式的正向价值：它不仅是故障兜底，还是实验基准。同一套代码，开关切在 L1 就是对照组、切在 L0 就是实验组，保证两组除决策模式外的一切（限流、预算、pacing、对账）完全同构——单一变量原则的工程化保证。

执行：统计口径与结论纪律

  • 样本量先行：按基线 CPA、α=0.05、统计功效 0.8、预期最小可感知效果（MDE≈8%）反推最小样本量，样本不足不开实验（「样本量不够，p 值毫无意义」）；
  • 周期覆盖完整周：至少 7 天，覆盖工作日/周末流量形态差异（动态雷达行业共识）；
  • 固定 horizon：预设 7 天读数一次，不天天偷看——频繁看结果会严重高估效果（多重检验问题）；
  • 结论格式：不止报 p 值，报效果区间（CI）——「CPA 下降 12% [置信区间 7%~17%], p<0.01, n=xx 万决策」；统计显著之外给出商业显著的一句话（按当前预算规模，年化节省多少）。

验收预期与「CPA 12%」的数字纪律

  • 实验组 CPA 相对下降 ≈12%（funnel.yaml 参数化设计使该结果可复现且非作弊——两组用户面对相同的转化概率分布，差异全部来自决策策略本身，M0 防作弊设计在此收线）；
  • 护栏全绿：花费偏差 < 5%、SRM 零触发、两组决策 P99 差 < 1ms（实验组多跑策略引擎但缓存命中下成本可控）；
  • 诊断链完整：任一 CPA 差异都能下钻到 reason 码层面（如「实验组 R1 拒绝率 18% vs 对照组 0——已购误投的消除即下降来源」）；
  • 简历数字的诚实口径：12% 是模拟器漏斗参数下的实验结论——简历写作时必须能说清「模拟环境的对照实验」，绝不含糊其辞为「线上优化 12%」（面试诚实性红线，也是追问时的加分坦诚）。

06三张速览卡

卡1 · 归因口径速查
  • 模型：末次点击（LCA）——Microsoft/Apple 行业默认，对齐账单口径、可解释、与已购保护业务语义一致
  • 窗口：7 天（行业默认 30 天的裁剪：电商拉新决策周期短，窗口越长稀释越强）
  • 计数：All（每次转化都计，购买语义）而非 Unique
  • 匹配链：transUniqueId → click ZSet（7 天）→ requestId 反查决策 → 归因日志（不可变事实，口径调整走版本化重放）
  • 未归因率：<5% 是告警线不是统计线——回流断链的哨兵
卡2 · 回流链路与近线更新
  • 拓扑：归因 → mini-MQ → 双消费组（特征更新 / 指标聚合），物理隔离、独立 lag 告警
  • <5s 五段账：归因 0.1s + MQ 发布 1s + 消费 2s + 更新生效 2s
  • 近线定位：比实时便宜、比离线新鲜；T+1 更新 = 自废 RTA 武功
  • 幂等纪律：覆盖式更新（set 非 incr）；计数特征 requestId 去重
  • 可见延迟：回流 5s + L1 刷新 15s ≈ P99 20s——7 天粒度业务对 20s 无感（「不需要更快」是加分回答）
卡3 · 实验设计三件套
  • 分桶：MurmurHash3(userId, salt=experimentId) % 1000，确定性可复算；互斥（同资源池/强感知）vs 正交（不同环节、salt 隔离）
  • 准入：AA 测试通过才开 AB（先证分桶无偏）；SRM 常态检测（触发即熔断读数）
  • 指标三分层：北极星（CPA）/ 护栏（花费偏差、SRM、P99）/ 诊断（reason 码分布）
  • 结论纪律：样本量先行（α=0.05, power=0.8, MDE 8%）+ 固定 horizon + 报 CI 不只报 p
  • 对照组复用：人群包模式 = KillSwitch L1 的正向价值——降级即基准
