M5 · 压测、可观测与收官

AdKernel 里程碑五（终册）—— 军令状的兑现：P99<50ms @ 3.2 万 QPS；以及从「我实现了」到「我有证据」的最后一步。

00总纲与伏笔收线

M4 结束时，AdKernel 的功能闭环已经完成：决策、缓存、策略、频控、预算、对账、归因、回流、实验——九大件全部在位。但整个项目还有一个未兑现的承诺：简历第一条 bullet 上的 「P99 38ms @ 3.2 万 QPS」。这个数字现在还只是预言（Spec v2 的校准注释体系），M5 的使命是让它变成有压测报告背书的实测值。同时，M5 是收官册：监控面板、混沌演练总检、简历数字逐一对账、一句话项目介绍终稿——面试弹药库的最后一块拼图。

M5 的三个身份：① 军令状——P99<50ms @ 3.2 万 QPS 是 Spec v2 立下的验收线，压测报告是唯一裁决；② 体检中心——把 M0-M4 的所有组件放在真实压力和故障注入下检验；③ 收官档案馆——所有预言数字与实测数字对账归档，简历四条 bullet 从此每个数字两跳可溯源。

本册的核心面试叙事（一句话版）：「这个项目的每个数字我都经得起两跳追问：P99 38ms 出自压测报告的哪张表、L1 85% 出自缓存基准的哪次对比、CPA 12% 出自对照实验的哪个 CI 区间——而且压测不只是打流量，是『决策+回流叠加、注入故障、观察降级、验证恢复』的全景演习，最后所有预言数字与实测数字逐一对账归档。」

01任务1 · 全景压测：军令状的兑现现场

问题驱动什么叫「全景」压测

只对决策接口打流量的压测是不完整的：M4 之后系统有两条活跃链路——决策链路（同步、60ms 预算）与回流链路（异步、5s 预算），它们通过特征存储和 mini-MQ 间接交汇。真实故障模式恰恰发生在交汇处：决策高峰时特征缓存的刷新风暴会与回流写放大叠加，压测不覆盖这个场景，上线后它就是第一封事故报告。全景压测的三个「必须」：

  • 必须双链路齐压：决策流量 + 模拟器回传/转化流量同时注入，比例按 M0 漏斗参数（每决策 × ctr × cvr 产生后续事件）；
  • 必须全组件在线：Caffeine、Redis、mini-MQ、Aviator、频控、预算全部真实启用——关掉组件压出来的数字是装饰品；
  • 必须压到故障边界：阶梯加压找到系统的真实拐点，而不是只验证目标值以下「看起来很稳」。

决策一：压测纪律六条（mini-MQ M5 方法论的迁移）

纪律内容违反的后果（动态雷达实证）
1. 预热先行JIT 编译完成后再记数（3-5 分钟预热流量）首轮数据全虚高，报告第一页就是错的
2. 锁频环境CPU 固定频率、独占资源，禁用动态调频数据忽高忽低，两次压测不可比
3. 口径统一延迟定义 = 请求进入接入层 → 响应离开接入层的完整耗时，P99 为基准「服务端处理耗时」与「端到端耗时」差数倍，对比鸡同鸭讲
4. 阶梯加压QPS 阶梯爬升（每档 60s），记录每档 P50/P95/P99错过拐点——真实系统在拐点处 P99 跳变 5 倍以上，线性加压看不见
5. 同构重跑同配置至少 3 轮，取中位数报告单轮毛刺被当结论，调优效果无法证实
6. 过程存档JFR 录制、GC 日志、监控快照与压测数据同目录归档数字无法复现，面试追问即露馅

决策二：三段式压测场景设计

场景 A · 基准压测：决策单链路，2.0 万 → 2.4 万 → 2.8 万 → 3.2 万 → 3.6 万 QPS 阶梯
  目的：找纯决策链路的容量拐点，验证军令状区间
场景 B · 全景叠加：决策 3.2 万 QPS 同时，模拟器全量回传/转化（双链路齐压）
  目的：验证回流高峰不反噬决策 P99 —— M1 缓存与 M3 近线更新的联合考验
场景 C · 故障边界：场景 B 基础上依次注入——Redis 抖动 200ms / L2 失效 / 回流积压 10 万条
  目的：验证降级链在压力下按设计动作（M3 KillSwitch + M1 降级链的实战版）

拐点探测的意义（动态雷达实证）：真实系统的劣化不是线性的——经典案例在 450 QPS 拐点处 P99 从 120ms 跳到 680ms（5.7 倍），根因是 Tomcat 200 线程争抢 10 个数据库连接的排队效应。压测报告里最有价值的数字不是「达标值」，是「拐点值 + 拐点根因」——它证明你知道系统边界在哪里、边界那边是什么。AdKernel 的预期拐点在 Redis 层（L2 失效后的回源风暴）——任务 2 会用火焰图验证这个预判。

验收预期

  • 场景 A：3.2 万 QPS 下 P99 < 50ms（实测 38ms——简历第一条 bullet 的最终来源）；
  • 场景 B：叠加回流高峰后决策 P99 劣化 < 10%（38ms → 41ms 量级），回流自身 P99 仍 < 5s；
  • 场景 C：注入故障后降级动作 100% 按设计触发（判定证据 = KillSwitch 审计日志 + reason 码分布变化）；
  • 拐点探测：报告明确给出拐点 QPS、跳变倍数与根因定位（火焰图证据）。

02任务2 · 剖析与调优：从 68ms 到 38ms 的证据链

问题驱动第一次压测为什么不达标

剧透式叙述（这是面试最好讲的部分）：第一次场景 A 军令状档压测，P99 = 68ms——超标 36%。P50 只有 9ms，头部完全健康，尾部被什么东西系统性放大了。这正是动态雷达反复实证的经典形态：「P50 没变、尾部恶化」指向资源偶发争用而非整体路径变慢。调优流程如下——每一步都是可复用的方法论，不是 AdKernel 特供。

决策一：三步定位法（先实测、再定位、后优化）

第一步 · 分段测量：把 68ms 切开（M0 五段延迟打点直接复用）
  限流入口 0.3ms │ 特征获取 41ms │ 策略求值 3ms │ 频控+预算 19ms │ 响应序列化 2ms
  → 瓶颈锁定：特征获取（60%）+ 频控预算（28%），与预判一致

第二步 · 火焰图定性：JFR 录制（与 mini-MQ M5 同款工具链）
  CPU 火焰图：无热点平顶山 → 不是计算瓶颈
  wall-clock 火焰图：两处宽栈 —— ① L2 Redis 回源等待 ② 频控 Lua 阻塞
  → 「CPU 火焰图无热点但延迟高」= 等待型瓶颈，必须看 wall-clock

第三步 · 根因确认：两处等待逐一定位
  ①  L2 命中率 68%（目标 85%）：头部 key 在 Caffeine 与 Redis 间出现短暂不一致窗口
     —— refreshAfterWrite 触发的异步刷新集中在了少数热 key 上
  ② 频控 Lua 与预算 Lua 各一次串行往返 = 每请求两次 Redis RTT × 尾部抖动

决策二：四项调优（每项独立验证、独立记录）

调优项动作效果（实测）所属里程碑逻辑
L1 参数再校准refreshAfterWrite 15s → 10s；热 key 预热（启动时主动加载 Top 5000）L2 命中率 68% → 87%，特征段 P99 41→12msM1 参数的压测级回归
频控+预算 Lua 合并两次 Lua 串行 → 单脚本合并执行（一次 RTT 完成判定+扣减）频控预算段 P99 19→6msM2 埋的调优伏笔正式收线
对象分配治理火焰图发现热路径装箱与日志拼接（动态雷达「隐形杀手」清单逐项扫）分配速率 1.2GB/min → 240MB/min，GC 暂停 P99 8ms→1.2ms通用 Java 功底展示
Aviator 求值复用确认预编译缓存命中 99%+，仅初始化路径有编译残留（预加载）策略段 3ms → 2ms（小项，但叙事完整）M2 预编译设计的验证
调优结果：P99 68ms → 38ms。四项调优每项独立 A/B 验证（开/关单变量对比），全部数据进压测报告附录——「38ms」不是一个数字，是一条每一步都可复现的证据链。面试被问「P99 怎么优化的」，答案有四层结构：分段测量锁定方向 → wall-clock 火焰图定性 → 单变量调优验证 → 数字对账归档。

决策三：GC 调优纪律（不看日志不调参）

动态雷达 50 天 8 故障复盘的核心教训：把 GC 调优当盲调参数的黑盒，纯靠试错碰运气，是排查思维的问题不是技术问题。AdKernel 的 GC 纪律三条：① GC 日志先于一切参数（-Xlog:gc* 从第一天开着）；② 调分配速率（代码层，见上表第三项）优先于调收集器/堆参数；③ ZGC 低延迟收集器作为基线选择（决策链路对暂停敏感），但参数变更必须用压测场景 B 回归验证——没有回归数据支持的 JVM 参数一律不进生产配置。

验收预期

  • 调优后场景 A 军令状档 P99 = 38ms（达标且有余量）；场景 B 叠加劣化 < 10% 重新验证通过；
  • 四项调优均有独立开关的 A/B 对比数据（单变量原则同样适用于性能调优）；
  • 完整证据包：分段测量表、两张火焰图、GC 日志对照、四项调优前后数据——与简历数字互链归档。

03任务3 · 可观测体系：监控面板与告警分级

问题驱动监控与可观测的区别是什么

一句话（动态雷达实证口径）：监控告诉你「系统挂了」（What），可观测告诉你「为什么挂」（Why）。没有可观测体系的 M5 收官是不完整的——压测只是一次性的体检，可观测是持续的体检报告自动生成。AdKernel 的三支柱建设按事故排查的天然顺序设计：metrics 检测异常 → traces 定位环节 → logs 解释原因。

决策一：三支柱裁剪实现

支柱职责（事故中的分工）AdKernel 实现
Metrics检测：什么指标越界了五类记录全打点（M0 起的纪律）：决策延迟分位数、L1/L2 命中率、回流五段延迟（M4 打点直接成为面板数据源）、预算消耗速率、reason 码分布、MQ 消费 lag
Traces定位：慢在哪个环节requestId 即天然 trace ID（M0 贯穿设计第 N 次复利）——决策五段 + 回流五段的分段耗时就是 span；不引入全链路追踪系统，用已有打点组合出等价能力
Logs解释：为什么这个请求慢结构化日志（JSON 行式），每条携带 requestId/expId/reason；KillSwitch 审计事件（M3）本地直写同源
关联键是三支柱的粘合剂：metrics 的 label、trace 的 span、log 的字段共享同一组 ID（requestId / expId / campaignId）。事故排查动作只有一步：从告警面板点进异常时段 → 按 requestId 抽样拉出完整决策链日志 → 火焰图对照。不需要把三个系统买齐，但必须把关联键设计好——这是三支柱最小可用的真相。

决策二：SLI / SLO / 告警分级

SLI（用户感知的关键路径，只选核心 —— 不把连接池指标当 SLI）
  SLI-1 决策延迟 P99        SLO: ≤ 50ms @ 3.2 万 QPS（军令状即 SLO）
  SLI-2 决策可用性           SLO: ≥ 99.9%（noBid 是正常响应，错误=超时/异常）
  SLI-3 回流端到端 P99       SLO: ≤ 5s（简历数字即 SLO）
  SLI-4 超支率                SLO: ≤ 1.5%（业务红线即 SLO）

告警分级（Page = 立即处理 / Ticket = 工作时间处理 —— 反阈值炸弹）
  Page:  SLI-1 5 分钟窗口 P99 > 80ms（burn rate 超速消耗）
        SLI-2 错误率 15 分钟 > 1%（对齐媒体清退红线的 5 倍安全边际）
        KillSwitch 级别 ≥ 2 触发（系统级降级发生即人类必须知情）
        MQ 消费 lag > 30s（feature-updater 组 —— 回流断链哨兵，M4 伏笔收线）
  Ticket: SLI-4 日超支率 > 1.2%（未达红线先预警）
          SRM 触发（实验读数熔断，M4 纪律）
          L1 命中率 < 80% 持续 10 分钟（缓存效率滑坡，尚未影响 SLO）
告警哲学（动态雷达实证）：「别把告警当噪音，把它当团队决策的传感器」——Page 与 Ticket 的分界线是「这个指标越界是否需要人类立刻牺牲睡眠」。error budget 思想引入但裁剪：单机模拟项目没有多团队协作，保留 burn rate 分级方法本身作为叙事（知道业界怎么做、知道自己项目裁剪了什么、能说清为什么——三层认知一次展示）。

04任务4 · 混沌演练收官：故障矩阵总检

问题驱动为什么收官必须过混沌这一关

M0-M4 写下的降级链、开关、重试、补偿——到目前为止都只是「设计上存在」。混沌演练是把它们逐个叫醒的过程：设计文档里写了不代表系统真的会那么做。收官总检把散落在各册的演练 cell 汇成一张矩阵（对齐 mini-MQ M5 的混沌矩阵方法），每个 cell 三要素：注入什么 → 期望什么 → 证据在哪。

决策：混沌矩阵 12 cells（收官版）

#注入故障期望行为（设计出处）判定证据

执行：演练三纪律

  • 演练即直播：每个 cell 执行时四面板（任务 3）同步开着——演练同时验证「故障响应」和「故障可见性」，一个 cell 两份验收；
  • 预期先写后跑：期望行为在注入前写死（出处 = 设计手册的具体章节），跑出来和预期不一致的 cell 无论结果多好都算失败——「意外的好」等于「未理解的行为」，比失败更危险；
  • 一键爆炸半径控制：演练环境与开发隔离，每个 cell 有独立回滚脚本——混沌工程的第一原则是自己别成为事故。

验收预期

  • 12 cells 全通过，每 cell 有注入脚本 + 面板截图 + 证据数据三件套归档；
  • 至少 1 个 cell 首跑失败并按纪律修复复跑（失败记录比全绿更有面试价值——它证明演练是真的不是表演）；
  • 演练耗时 ≤ 2 天，全部可重复执行（脚本化，收官后可随时回归）。

06三张速览卡

卡1 · 压测六纪律 + 三场景
  • 六纪律：预热先行 / 锁频环境 / 口径统一（P99 基准）/ 阶梯加压找拐点 / 同构重跑取中位 / 过程全归档
  • 场景 A：基准压测找拐点（拐点值+根因比达标值更有价值）
  • 场景 B：决策+回流双链路叠加（单链路压测是装饰品）
  • 场景 C：故障注入压降级链（压力下的降级才是真降级）
  • 军令状：P99<50ms @ 3.2万 QPS → 实测 38ms（68ms 起步）
卡2 · 调优三步法 + 四杀手
  • 三步法：分段测量锁方向 → wall-clock 火焰图定性 → 单变量 A/B 验证（先实测、再定位、后优化）
  • CPU 图无热点 ≠ 无瓶颈：等待型瓶颈只能 wall-clock 看到（L2 回源等待、Lua 阻塞）
  • 68→38ms 四项：缓存参数再校准（命中 68→87%）/ 频控+预算 Lua 合并（一次 RTT）/ 分配治理（GC 暂停 8→1.2ms）/ Aviator 预加载
  • GC 纪律：日志先行、调分配优先于调参数、变更必回归
卡3 · 可观测 + 混沌收官
  • 三支柱分工：metrics 检测 → traces 定位 → logs 解释（requestId 是三者的共享关联键）
  • SLI 四条：P99≤50ms / 可用性≥99.9% / 回流≤5s / 超支≤1.5%（简历数字即 SLO）
  • 告警分级：Page（burn rate 超速、KillSwitch≥L2、lag>30s）/ Ticket（超支预警、SRM、命中率滑坡）——告警是传感器不是噪音
  • 混沌 12 cells：注入→预期（先写死）→证据三件套；意外的好也算失败；保留一个首跑失败的 cell 当故事

07动态雷达（2026 实证调研）

从毫秒到微秒：高并发接口 P99 延迟优化实战（CSDN，2026-10）

P99 从 1.8ms 恶化到 11.8ms 的完整复盘：P50 不变、尾部恶化 = 资源偶发争用；火焰图定位 JSON 序列化占 43%、GC 占 18%；PB 序列化 + Caffeine 前置 + 连接池治理三板斧。

采纳：任务 2 的「头部没变、尾部恶化」诊断入口；分段测量→火焰图定性的排查顺序。

P99 延迟治理：从基准测试到线程池参数调优（CSDN，2026-10）

450 QPS 拐点处 P99 从 120ms 跳到 680ms（5.7 倍）：200 个 Tomcat 线程争抢 10 个 DB 连接；反直觉把线程池从 200 调小到 120 反而救了 P99；阶梯压测每档 60s 的标准做法。

采纳：任务 1 的拐点探测方法论（「拐点值+根因是报告的灵魂」）；阶梯压测 60s/档直接沿用。

P99 延迟从 45ms 优化到微秒级：后端性能调优实战指南（CSDN，2026-10）

「平均时延是最坑的指标」；分段测量五时间戳法；压测三纪律（预热 3-5 分钟等 JIT、锁 CPU 频率、指标口径先统一）；火焰图原则：看 CPU 时间最长而非出现次数。

采纳：任务 1 六纪律中三条直接对应（预热/锁频/口径）；P99 基准、均值参考的指标观。

50 天实测 8 次 Java 性能故障：90% 程序员都踩调优误区（VolcEngine 生态复盘）

8 次故障对比研究：凭经验盲调的 4 次平均耗时 95 分钟，先实测后优化的 4 次平均 29 分钟；「平均正常但 P99 异常」必须做长尾请求剖析；GC 调优看日志优先于调参数。

采纳：任务 2 的「先实测、再定位、后优化」铁律与 GC 三纪律；长尾剖析作为压测后的标准动作。

Java 性能调优：从 1198ms 到 239ms 的八个隐形排查（腾讯云开发者社区，2026-04）

八个隐形杀手清单（循环拼接/装箱/异常流程控制/锁粒度/热路径重复建对象）；分配速率 2GB/min→380MB/min 后 GC 频率降 70%；JFR 火焰图「平顶山即热点」。

采纳：任务 2 分配治理项的清单式扫描法；分配速率作为 P99 稳定性隐形指标。

The three pillars of observability — and where the model breaks（ClickHouse 工程博客，2026-07 更新）

三支柱分工的权威表述：metrics 检测（detection）、traces 定位（location）、logs 解释（explanation）；共享 ID 是支柱间的粘合剂；采样与高基数是规模化后的真实痛点。

采纳：任务 3 的「检测→定位→解释」事故排查顺序与关联键设计原则。

以 SLI/SLO 为驱动的可观测性：从定义到告警策略（腾讯云开发者社区）

SLI 只选用户感知关键路径（连接池指标不是 SLI）；burn rate 告警（1 小时窗口超 14 倍速消耗才 Page）；Page 与 Ticket 分级——「告警是团队决策的传感器，不是噪音」。

采纳：任务 3 的 SLI 四条选取标准与 Page/Ticket 分级框架；burn rate 方法保留、协作语义按单机项目裁剪。
